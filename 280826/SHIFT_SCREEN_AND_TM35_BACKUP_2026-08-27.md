# Экран смены + резервирование tm35 — отчёт (27.08.2026)

## 1. Экран смены (`/shift`) — сеточный ежедневный ввод факта

Задача координатора: заменить одиночную форму `/form` сеткой, чтобы
инженер ПТО мог полностью отказаться от Excel-графика для ежедневного
факта. Построено, задеплоено на `tm.asd-kontur.ru`, проверено вживую.

### Разведка перед разработкой

- **`POST /api/gantt/cell`** — не построчный инлайн-грид, а модалка:
  клик по дню открывает окно на все поля разом (план/факт людей,
  причина, комментарий), одно сохранение. Апсерт в `daily_progress` по
  `(date, work_id, source='web_form')`, `audit_log.action='gantt_cell_edit'`.
- **`POST /form`** — тот же ключ апсерта; дополнительно при непустом
  `fact_pct` обновляет `work.fact_pct` (читают `/dashboard`, `/gantt`,
  `/works`). `audit_log.action='web_form_submit'`.
- **«Работа актуальна на дату» — проверено данными, не предположено.**
  Наличие строки в `daily_progress` за последние 7 дней есть у 165 из
  165 работ (артефакт календарной матрицы Excel-импорта) — не сигнал.
  `baseline_schedule` с уверенностью high/medium тоже не годится
  фильтром по умолчанию — у 42 из 114 незавершённых работ такого
  baseline нет вовсе, фильтр по нему запер бы именно тех, кому нужно
  отчитаться. Выбран фильтр `work.status not in DONE_STATUSES` — тот
  же критерий, что уже использует переключатель «только активные» на
  `/gantt` → 114 из 165 работ по умолчанию, «показать все» → 165.

### Что построено

`/shift` (страница) + `GET /api/shift` (чтение) + `POST /api/shift/cell`
(сохранение) + переиспользован существующий `POST /api/gantt/work` для
добавления работы прямо с экрана.

- Дата вверху (по умолчанию сегодня), смена перезагружает сетку.
- Колонки: шифр · наименование · участок · % готовности · люди ·
  простой (тот же `REASON_CODES` из `main.py`) · комментарий · статус.
- **Частичное сохранение по колонке** — каждое поле сохраняется своим
  upsert'ом, `SET`-часть трогает только свою колонку. Несколько
  инженеров ПТО могут одновременно редактировать разные поля одной
  строки, не затирая друг друга — гарантия на уровне SQL, проверено на
  живых данных (бэкдейт-запись содержала только `fact_pct`, остальные
  поля `NULL`).
- Клавиатура: Tab/Shift+Tab — нативный порядок DOM. Enter/↓/↑ —
  сохраняют и двигают фокус по той же колонке. ←/→ — переход в соседнюю
  колонку только когда курсор в начале/конце текста. Стрелки на
  `<select>` намеренно не перехватывались — там нативное переключение
  значения важнее.
- Статус строки: не заполнено / заполнено (зелёная плашка, время
  последнего изменения в тултипе) / сохранение… / ошибка (текст ошибки
  сервера в тултипе, инпут не сбрасывается).
- Placeholder — текущий `work.fact_pct`, если за день ещё ничего не
  введено. Чисто информационно, не отправляется.

**Решение, принятое самостоятельно (не переспрашивал):** колонка
«Люди» — факт (`actual_crew`) за смену, не пара план/факт. Планирование
людей остаётся на `/gantt` и в `/form`. Если имелось в виду другое —
поле легко расширить, апсерт уже параметризован по колонке.

### Проверка (живым браузером, Playwright, `1366×768`, реальный Basic Auth)

- Деплой сверен `docker exec` (не диском сервера).
- Скриншот после hard-reload — реально просмотрен: строки таблицы,
  пустые поля ввода, статус «не заполнено» серым; после правки —
  зелёная полоса слева на строке, значения на месте, статус «заполнено».
- Клавиатура пройдена по-настоящему: Tab между колонками одной строки;
  Enter переводил фокус на следующую строку той же колонки; ArrowUp —
  обратно.
- Сохранение пережило полный `reload()` (не только `render()`);
  `source='web_form'` в БД подтверждено запросом.
- Бэкдейт (сегодня−5 дней) — независимая пустая запись на ту же
  работу, другую дату, заполнена и сохранена отдельно от сегодняшней.
- Добавление работы с `/shift` — реально создало строку в `work`
  (`TM35-AUX-147`), после проверки удалена.
- Регресс — 13 маршрутов (`/dashboard /today /report /blockers /form
  /shift /id-packages /changes /prescriptions /gantt /data /critical
  /works`) — все 200, 0 консольных ошибок, 0 сетевых 4xx/5xx.
- Найден и исправлен до сдачи: Enter/стрелки вызывали двойное
  сохранение одного значения (лишняя запись в `audit_log`, данные не
  терялись) — поправлено оптимистичной пометкой «отправлено» перед
  запросом, перепроверено.
- Все тестовые записи (`daily_progress` за 2 даты, тестовая работа,
  связанные `audit_log`) удалены с `select` до/после.

### Не чинилось в рамках задачи (как и просил координатор)

Расхождение `REASON_CODES`/`downtime_cause`, английские статусы на
`/changes`/`/prescriptions`, `None` в подписи на `/report`, отсутствие
формы стоп-фактора, отсутствие ролей/авторизации.

## 2. Резервирование базы `tm35`

### Находка (до правки, 27.08.2026 днём)

`/opt/kat/backup.sh` дампил **только `kat_core`**
(`pg_dump -U kat_admin kat_core`, ежедневно 03:00, `kat_core_*.sql`,
заливка на Я.Диск). База **`tm35` не резервировалась вообще** — ни
строки в скрипте, ни файла в `/opt/kat/backups/`, кроме одного
разового ручного дампа (`tm35_20260827_030305.dump`, 550 КБ, снят
вручную кем-то из предыдущей сессии, без повторения).

Пока рядом есть Excel — он де-факто второй экземпляр данных. После
отказа от Excel единственный экземпляр — база, у которой не было
резервной копии.

### Правка

`/opt/kat/backup.sh` дополнен веткой `tm35` (custom-формат `-Fc`,
как у единственного ручного дампа): `pg_dump -Fc tm35` →
`/opt/kat/backups/tm35/tm35_${DATE}.dump` → `rclone copy` на
`yadisk:postgres_backup/tm35/` → недельная ротация. Старый скрипт
сохранён как `/opt/kat/backup.sh.bak.20260827_before_tm35`. Синтаксис
проверен (`bash -n`), связка дамп→заливка проверена вручную сухим
прогоном — сработала, тестовый файл удалён и локально, и с Я.Диска.

### Статус на 27.08.2026 16:55 MSK — резервируется ЧАСТИЧНО

Механизм внедрён и вручную подтверждён рабочим end-to-end, но
**ни одного самостоятельного, кроном порождённого дампа `tm35` ещё
нет** — правка внесена днём, следующий пуск `crontab`
(`0 3 * * * /opt/kat/backup.sh`) — ближайшие 03:00 MSK, ещё не
наступили на момент проверки. Наличие строки в crontab само по себе не
доказательство успешного выполнения.

**Проверить после 03:00 MSK**: `ls -la /opt/kat/backups/tm35/` должен
показать новый файл со свежей датой (не только старый от 27.08 03:03).
Если файла нет — значит cron либо не запустился, либо упал молча,
самостоятельная проверка станет следующей задачей.
