## 2. КРИТИЧЕСКАЯ НАХОДКА — справочник статусов НЕ общий для всех вкладок

ТЗ прямо утверждает: «список идентичен на всех проверенных вкладках»
(§2). **Проверено по факту на всех 18 вкладках — это не так.**

- **16 из 18 вкладок** используют один и тот же 8-позиционный список:
  да/Сделано в эл.виде · нет/Не сделано · Х/Работы не производятся ·
  Передано на проверку · Подписано · Нет проектного решения · Есть
  замечания · Нет лаборатории.
- **Только «ОПН»** использует другой, 9-позиционный список с циклом
  проверки РСК: да/Сформировано в эл.виде · нет/Не приступали ·
  Первичная проверка РСК · Устранение замечаний 1 · Повторная проверка
  РСК · Устранение замечаний 2 · Подписано · Нет проектного решения ·
  Замечания к площадке.

**Это прямо касается раздела 5 ТЗ (регламент просрочки).** Расчёт
«висит в „Первичная проверка РСК“ дольше 3 дней» опирается на стадии,
которых **нет в списке статусов 16 из 18 вкладок** — там просто нет
значения «Первичная проверка РСК» вообще. Регламент просрочки в
текущей формулировке ТЗ вычислим только для ОПН. Схема БД сделана per-
tab (`id_form_status.tab_id`, не общий справочник) именно из-за этой
находки — решение не форсировано молча, отражено структурой данных.
**Открытый вопрос координатору/ПТО**: какой список актуален — расходится
ли ОПН специально (более зрелый процесс) или наоборот отстал от
остальных вкладок.

## 3. На каком уровне ведётся запись — не выведено однозначно, сделан каскад

Посчитано по данным (не угадано): всего **666 строк раздел/конструкция**
и **~200 уникальных «разделов»** (без строгого дедупликейта по всей
книге) против **306 строк `id_package`**. Ни та, ни другая сумма не
совпадает с 306 ни в каком разумном приближении.

Отдельно: сама структура Excel — это матрица (строка-конструкция × вид
работ) → статус, то есть по факту данных атом **мельче**, чем «один
раздел» (что буквально сказал ПТО). Реализован **каскад**, как и
просило задание при неоднозначности: вкладка → раздел/конструкция → вид
работ, оба уровня — самостоятельные поля формы, `id_form_entry.
work_type_id` допускает `NULL` (вкладки без деления на виды работ, типа
СОДК, всё равно проходят). Не решал молча, вопрос — в описи находок.

## 4. Модель данных — append-only, подтверждено

Каждая отправка формы — **новая строка** `id_form_entry`, не
перезапись. Текущее состояние — последняя запись по паре `(row_id,
work_type_id)`.

**Проверено вживую**: одна и та же пара (раздел, вид работ) на «ОПН»
— три последовательные отправки (создание → смена статуса вперёд →
смена статуса назад) дали **три строки** в `id_form_entry` с одним и
тем же `row_id`/`work_type_id`, не одну перезаписанную.

`audit_log.old_value` — раньше мёртвая колонка, **теперь заполняется**.
Проверено: смена статуса вперёд дала `audit_log.old_value =
{статус до}`, `new_value = {статус после}`; смена назад — наоборот,
оба значения и автор (`user_id`) видны в одной строке лога.

## 8. Форма `/id-entry` — состав ровно по ТЗ §3

Поля в заданном порядке: вид сборки (вкладка) → ответственный →
раздел/конструкция/участок → вид работ/этап → статус + дата (по
умолчанию сегодня) → планируемая дата передачи в РСК → стоп-фактор →
комментарий. Одна форма для всех, поля 1–3 перестраиваются по вкладке
(проверено на 3 разных вкладках — «ОПН», «Труба Сварка», «СОДК», числа
опций совпали с реальным количеством строк/видов работ каждой
вкладки). Стоп-фактор переиспользует существующий `blocker`
(`blocker_type='design_decision'` — не идеальное семантическое
совпадение, ближайшее из существующих значений enum, решение
задокументировано в коде, не расширял enum ради этого).

Своих полей сверх ТЗ не добавлял. Массовую отметку не делал (ТЗ:
«желательно, не критично, не в первую очередь»).
