# Контур ИД — проект схемы под обе ветки развилки (28.08.2026)

**Статус: ПРОЕКТ, не применено к БД.** Ждём ответов ПТО на 25 вопросов
(брифинг §7, три ключевых — повторяется ли цикл замечаний, атом учёта
папка/документ, знает ли ПТО состав work→id_package). Этот документ не
решает развилку — готовит обе ветки, чтобы после ответа ПТО не терять
время на проектирование с нуля.

## Живая схема на 28.08.2026 (ПРОВЕРЕНО, `information_schema.columns`)

`id_package` (306 строк): `status_code` (живой S00…S90 конвейер) +
набор дат `formed_date`, `date_rsk_review`, `date_review_remarks`,
`date_fix_remarks`, `date_repeat_check`, `date_rsk_signoff`,
`date_scan_sdo` (мёртвые, старый импорт) + параллельный набор
`date_s10_formed` … `date_s90_closed_ks` (частично живые, см. брифинг
§3.3) + `status_formation`/`status_formation_raw` (третья, независимая
величина). `change` (0 строк, 22 колонки), `prescription` (0 строк, 20
колонок) — схемы готовы, наполнения нет. `work` уже имеет FK
`id_package_id`, `change_id`, `prescription_id` — объявлены, кодом не
используются (0 обращений, ПРОВЕРЕНО grep).

## Общая часть — не зависит от исхода развилки

Нужна в любом случае, можно делать уже сейчас:

1. **Форма «Карточка папки ИД»** (create/update `id_package`): шифр
   (`section_no`+`seq_no`), раздел, участок (`location`), состав
   (`composition`), сумма (`amount_no_vat`), ответственный
   (`responsible_pto_id` — FK на `app_user`, сейчас 2 строки, форма
   должна уметь заводить нового), плановая дата сдачи. Валидация: сумма
   ≥ 0, шифр уникален.
2. **Форма «Карточка ИЗМ»** (create/update `change`): номер, тема,
   статус (`status` — сейчас хранит английские DRAFT/REQUEST_SENT/OPEN,
   см. находку §6.3 брифинга — нужен словарь рус./англ., не выдумывать
   произвольный список статусов без подтверждения ПТО, взять из
   реального документа на согласование, если он есть).
3. **Форма «Карточка предписания»** (create/update `prescription`):
   номер документа, от кого (`source`), категория, участок, срок
   (`due_date`), связанная работа/папка (`work_id`/`id_package_id` —
   уже есть колонки), отметка закрытия (`actual_close_date`).
4. **Форма создания стоп-фактора** (`blocker`) — сейчас `insert into
   blocker` в коде нет вообще (находка §6.5 брифинга). Поля по образцу
   существующих 9 строк: `work_id` (nullable), `blocker_type`,
   `description`, `responsible_name`, `expected_resolution_date`.
5. **Настройки объекта** — форма для `app_setting` (директивный срок и
   расширение существующего key/value механизма на параметры ИД, если
   понадобятся).

Ни один из этих пяти пунктов не зависит от того, журнал событий или
набор дат победит — везде идёт по существующим полям `id_package`/
`change`/`prescription`/`blocker`, которые есть в БД уже сейчас.

## Ветка А — журнал событий (`id_package_event`)

```sql
-- ПРОЕКТ, не применено. Черновой DDL для обсуждения с координатором/ПТО.
create table id_package_event (
    id bigserial primary key,
    id_package_id bigint not null references id_package(id),
    event_type text not null,       -- 'formed'|'sent_to_rsk'|'objections'|
                                     -- 'fix_started'|'fix_done'|'recheck'|
                                     -- 'signed'|'scanned_sdo'|'closed_ks'|
                                     -- 'blocked_by_change'|'unblocked'
    event_date date not null,
    actor_id bigint references app_user(id),
    comment text,
    file_url text,
    related_change_id bigint references change(id),  -- для blocked_by_change
    created_at timestamptz not null default now()
);
create index on id_package_event(id_package_id, event_date);
```

- `status_code` перестаёт быть полем, которое правят вручную —
  становится производной от последнего события (view или
  вычисляется в запросе). Круг «замечания → устранение → повторная
  проверка» пишется как последовательность `objections`→`fix_done`→
  `recheck`, повторяется сколько угодно раз — счётчик кругов = `count(*)
  where event_type='objections'`, ровно то, чего просит экран «Почему
  отстаём».
- Блокировка ИЗМ (`S40`) перестаёт быть значением `status_code` —
  становится интервалом (`blocked_by_change` … `unblocked`), при снятии
  блокировки видно, на каком событии папка стояла до блокировки
  (проблема (в) брифинга §3.3 решается сама).
- `date_s10…date_s90` в `id_package` можно оставить как есть (не
  удалять — правило проекта) и рядом добавить генерируемые/пересчитываемые
  значения `min(event_date) where event_type=X` — старые дашборды,
  которые их читают, не ломаются.
- Стоимость: одна новая таблица, forms пишут в неё вместо прямого update
  статуса. `audit_log` в этой ветке становится избыточным для
  `id_package` конкретно (журнал событий и есть история) — но не
  удаляется, продолжает работать для остальных таблиц.

## Ветка B — набор дат в карточке (без журнала)

- Использовать уже существующие `date_s10_formed` … `date_s90_closed_ks`
  как единственный источник дат стадии, привести `status_code` к тому,
  чтобы он всегда был производным от заполненных дат (а не отдельно
  редактируемым полем — сейчас это два независимых способа узнать
  стадию, что и есть проблема (б) брифинга).
- Круг замечаний: если ПТО подтвердит «цикл всегда один», добавить одно
  поле `objections_round smallint default 0` (инкремент при каждом
  возврате), без истории самих кругов — экран «Почему отстаём» покажет
  только текущий счётчик, не даты каждого круга.
- Блокировка ИЗМ: `date_s40_blocked`/новое `date_s40_unblocked` — два
  поля вместо интервала в журнале, состояние «на чём стояла папка до
  блокировки» нужно сохранять отдельным полем
  (`status_code_before_block`), иначе проблема (в) брифинга не решается.
- Стоимость дешевле сейчас (без новой таблицы), но при первом же
  подтверждённом повторном цикле замечаний (что уже похоже на правду —
  брифинг явно фиксирует это как открытое наблюдение) потребует миграции
  на ветку А задним числом, без истории прошлых кругов — она нигде не
  хранилась.

## Почему предпочтительнее закладывать ветку А уже сейчас

Не решение за ПТО, а замечание для координатора: ветка А (журнал) —
надмножество ветки B (даты вычисляются как `min(event_date)` по типу
события), а обратного перехода без потери истории нет. Итоговое решение
всё равно за ПТО/координатором — этот документ только фиксирует
стоимость каждого варианта, чтобы решение принималось с цифрами, а не
вслепую.

## Что нужно от ПТО, чтобы закрыть развилку

Три ключевых вопроса из уже отправленных 25 (брифинг §7):

1. Повторяется ли цикл замечаний — нужна ли история каждого круга?
2. Атом учёта — папка целиком или документы внутри неё?
3. Известно ли ПТО, какие работы графика входят в какую папку
   (`work.id_package_id`)?

До ответа — миграция не применяется, формы не пишутся поверх
несуществующей схемы.
