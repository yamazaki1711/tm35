- Приложение — контейнер `tm_backend` (образ `kat-tm_backend`),
  FastAPI + Uvicorn, Python 3.12. Наружу — только через `kat_nginx`
  (basic-auth, HTTPS, домен tm.asd-kontur.ru).
- БД — контейнер `kat_postgres` (pgvector/pg16), база `tm35`, роль
  `tm35_app`. Тот же физический Postgres, что у `kat_core`, но отдельная база.
- Код в `/app` внутри контейнера: `main.py`, `analytics.py`, `db.py`,
  `tm_patch.py`, `weather_sync.py`, `templates/*.html`, `static/`.

### Ключевое правило деплоя

**`/opt/kat` на хосте НЕ источник истины для контейнера.** Файлы копируются
`docker cp <файл> tm_backend:/app/...`, для правок `main.py` — затем
`docker restart tm_backend`. Шаблоны `.html` подхватываются без рестарта
(Jinja2 auto-reload).

Читать актуальный код нужно **из контейнера**
(`docker exec tm_backend cat /app/main.py`). После любой правки — сверять,
что файл внутри контейнера действительно изменился.

### Периодические задачи

Планировщика внутри приложения нет. Единственный механизм — **root crontab
хоста**:

```
0 3 * * *  /opt/kat/backup.sh
20 3 * * * docker exec tm_backend python /app/weather_sync.py --mode daily >> /opt/kat/tm35-weather.log 2>&1
```

Второй параллельный планировщик не создавать.

## 2. Что это за проект

ТМ-35 — ОКС «Тепломагистраль-35» в Хабаровске. ИКС-Хабаровск обратился к
КАТ с просьбой взять на сопровождение завершение строительства (остаток
СМР ~20%, оценка примерная) и формирование ИД на оставшуюся часть работ.

**Два параллельных контура, единая БД:**

- **СМР** — доделки, устранение замечаний, ежедневный факт. Атом — **работа**.
- **ИД** — формирование исполнительной документации. Атом — **пакет/папка/
  шифр** (вопрос об атоме открыт, §7).

### Согласовано — не пересматривать, не переспрашивать

- **Учёт объёмов по видам работ ведётся В ПРОЦЕНТАХ, не в нормочасах.**
  Проценты вписывает инженер ПТО. `work.fact_pct` живая;
  `daily_progress.planned_hours/actual_hours/stop_hours` мертвы — **не
  оживлять, не выводить в интерфейс**.
- **Полный отказ от Excel как источника данных** — данные поступают в БД
  только через формы. Полномочия обязать ПТО перейти есть; вопрос только в
  готовности системы (см. отдельный документ «Критерии готовности»).
- Отключаемый Excel — ежедневный график ИКС/РСК на 3 листах. Реестр
  пакетов ИД попал в БД разовым импортом, постоянным источником не является.
- Координата объекта — одна константа на весь объект (48.4852 / 135.0815),
  по опорам/участкам не разносить.
- Telegram исключён окончательно. Модуль симуляции отложен, не в MVP.

**(а) Граф «работа ↔ норма ↔ пакет ИД ↔ ИЗМ ↔ предписание» спроектирован,

разовым скриптом по текстовому совпадению участка, результат **16,3%**.
СМР и ИД сейчас — две параллельные вселенные в одной БД.

**(б) В `id_package` живут ТРИ несогласованных описания состояния:**

1. `status_code` — линейный конвейер S00→S10→S20→S40→S60→S80→S90 (живой).
2. Даты из исходного Excel — **мёртвые**: `formed_date`, `date_rsk_review`,

   `date_rsk_signoff`, `date_scan_sdo`. Плюс `responsible_pto_id`,
   `signer_rsk_id`, `scan_pdf_url`, `change_id`.
3. `status_formation` — независимая величина из импортированного реестра:
   «да»/«нет»/«Схемы»/«Сформирована»/«Подписано». **Не перевод кода стадии**;
   совпадение текста для S10/S60 обманчиво.

Параллельно есть `date_s10_formed` … `date_s90_closed_ks` — частично живые;
`date_s30_objections`, `date_s50_resolved`, `date_s70_in_sdo` мертвы.

**(в) `S40 «заблокирован ИЗМ»` — флаг, а не стадия**, но лежит в том же
поле. При блокировке теряется информация, на каком этапе папка стояла.

## 8. Правила работы

1. **Не верить собственному отчёту «готово».** Проверять глазами на
   реальном скриншоте после hard-reload. Первая сессия отчиталась
   «готово» о вёрстке, которая на экране была полностью сломана.
2. **Сверять деплой внутри контейнера**, диск сервера не источник истины.
3. **Не удалять и не «чистить»** существующие компоненты, включая мёртвые
   и бэкап-таблицы.
4. **Никакого тихого фоллбэка** — либо явно, либо остановка с ошибкой.
5. **Находка не равна задаче.** Дефект вне периметра — в опись (§6), не
   чинить на месте.
6. **Тестовые записи в боевой БД** удалять сразу, с `select` до и после
   (относится и к тестовым БД/объектам — scratch-базы для проверки
   восстановления тоже удалять сразу после проверки).
7. **Не заканчивать ход вопросом и ожиданием подтверждения.** Нерешаемое —
   в список «требует решения координатора», очередь не встаёт.
8. **Отчёт — факты с метками** ПРОВЕРЕНО / НЕ ПРОВЕРЕНО / ПРЕДПОЛОЖЕНИЕ,
   с указанием, чем проверено. Без оценок и рекомендаций, если не просили.
