# Как работает «Разобрать и показать предпросмотр» (загрузка акта РСК)

Ответ по коду на kat-core, коммит `8e3ce53` (текущий деплой на момент
написания). Только чтение — код не менялся для этого разбора.

## 1. Где выполняется

- `POST /rsk/import` → `rsk_import_preview()`, `backend/main.py:7667-7697`
  (парсинг + расчёт диффа, ничего не пишет — см. §6).
- `POST /rsk/import/confirm` → `rsk_import_confirm()`,
  `backend/main.py:7700+` (запись после подтверждения).
- Сам парсер — отдельный модуль `backend/rsk_parser.py`, функция
  `parse_act(pdf_path)` (`rsk_parser.py:202`), импортируется в
  `main.py:24` (`from rsk_parser import parse_act`).
- Всё выполняется **внутри контейнера `tm_backend` на kat-core** —
  файл сохраняется на диск контейнера (`RSK_UPLOADS_DIR =
  backend/uploads/rsk_acts/`, `main.py:77-78`), `parse_act()` читает
  его оттуда тем же процессом uvicorn, никакого отдельного воркера или
  внешнего сервиса не вызывается.

## 2. Как парсится

- Библиотека — **pdfplumber** (`rsk_parser.py:15`, `import
  pdfplumber`), версия `0.11.10` (проверено `pip list` в контейнере —
  установлена, несмотря на устаревшую заметку в `docs/STATE.md` о том,
  что `pdfplumber` из `requirements.txt` не в живом образе; тот пункт
  устарел, отдельно не правил его в рамках этого разбора).
- Читается **текстовый слой PDF** (`extract_words()`/`extract_text()`),
  **не OCR** — в коде нет ни одного вызова распознавания изображений.
- Колонки — по **фиксированным координатам** `x = 56.0 / 90.5 / 323.9 /
  453.7 / 552.7` (`rsk_parser.py:17`, `BOUNDS`), не `extract_tables()`
  (тот метод пробовали раньше и отбросили — терял 73 из 152 строк,
  разорванные переносом страницы, см.
  `docs/RSK_ACT_PDF_IMPORT_2026-09-06.md`).
- Строки — по **горизонтальным линиям таблицы** (`page.rects` с
  `height < 2`, `rsk_parser.py:38`, `page_band_boundaries()`), не по
  диапазону между «якорями» (диапазонный метод пробовали и заменили —
  систематически ловил протечки на границах ячеек).
- Позиция (нарушение) внутри полос — начинается там, где ячейка колонки
  1 совпадает с `ANCHOR_RE = r"^№\s*(\d+)\s+(Повторно\b.*)$"`
  (`rsk_parser.py:178-187`) — печатный «№» плюс слово «Повторно» сразу
  после (не просто первое слово «№» — так ловились мусорные совпадения
  вроде ссылок на приказы или номеров граф журнала внутри чужого
  текста, см. тот же docs-файл).
- **Номер и дата акта** — из текста первой страницы (`title_text =
  pdf.pages[0].extract_text()`, `rsk_parser.py:91`):
  `ACT_HEADER_RE = r"АКТ ПРОВЕРКИ №\s*(4183-\d+)"` (`rsk_parser.py:22`)
  и `ACT_DATE_RE = r"«(\d{1,2})»\s+(\S+)\s+(\d{4})\s*г\."`
  (`rsk_parser.py:23`, дата словами по-русски — «11» августа 2026 г. —
  через словарь `RU_MONTHS`, `rsk_parser.py:24-27`).

## 4. Сканированный PDF (без текстового слоя)

**ПОПРАВКА 25.09.2026 (координатор закрыл находки №2/№3 ниже) — вывод
«исключения не возникает... но защиты в коде нет» ниже верен для
состояния на 25.09.2026 ДО этой правки, оставлен для истории. С
коммита, закрывающего эту правку, `/rsk/import` отклоняет такой файл
явным сообщением, не пишет ничего в базу — см. §7 ниже.**

Проверено на копии, в файл ничего не писалось: страница 1 акта
№4183-159 растеризована в изображение (`pypdfium2`, доступен в
контейнере) и пересобрана в PDF без текстового слоя (только картинка,
через Pillow). Подтверждено, что текстового слоя действительно нет:
`pdfplumber` `extract_text()` → 0 символов, `extract_words()` → 0 слов.

`parse_act()` вызван напрямую (не через `/rsk/import`, ничего в БД):

```
act: {'act_no': None, 'act_date': None, 'total_declared': None}
records count: 0
issues count: 0
checks: {'bands_total': 1, 'bands_with_anchor': 0, 'unique_sys_no': 0,
         'total_declared_in_act': None, 'no_remedy': 0, 'no_due_date': 0,
         'no_first_act': 0, 'no_item_no': 0, 'control_sections_found': 0}
```

**Исключения не возникает** — функция отрабатывает штатно и
возвращает пустой результат (0 позиций, номер/дата акта — `None`).
Через реальную форму `/rsk/import` это привело бы к предпросмотру с
«Позиций в акте: 0» и `act.act_no`/`act.act_date` — пустыми
(`rsk_import.html` рендерит `preview.act.act_no or '?'`, показал бы
«акт ? от ?»); настоящей защиты «это похоже на скан, распознавание
недоступно» в коде нет — предупреждения не будет, кроме нулевого числа
позиций на экране. Если бы пользователь всё же нажал «Подтвердить» —
запись в `rsk_act` упала бы на ограничении `act_no not null`
(`migrations/023_rsk_pdf_only.sql`), транзакция откатилась бы целиком
(ничего не запишется), но сообщение об ошибке было бы техническим, не
понятным ПТО. Это наблюдение, не фикс — задание было «без изменений
кода».

## 5. Отождествление нарушений между актами

Текущий (после правки координатора 25.09.2026, коммит `8e3ce53`)
алгоритм — **не по номеру**. Раньше (до этого коммита) ключом было
равенство печатного «№» из PDF; при переномеровке РСК это привело бы к
разрыву идентичности (новая запись вместо переноса старой, потеря связи
с `rsk_processing`). Текущий метод — `main.py:7515`
(`_rsk_match_new_act()`), похожесть нормализованного текста
(`norm_literal()` — lower + схлопывание пробелов, `backend/-
grafik_matching.py`) внутри одного раздела (`control_section`, жёсткий
предфильтр) через `difflib.SequenceMatcher`. Три порога
(`main.py:7486-7489`):

| Похожесть | Результат |
|---|---|
| ≥ 0.97 | почти точное совпадение — перенос сразу, без проверки отрыва от других кандидатов |
| ≥ 0.80 и отрыв ≥ 0.08 от второго места | уверенное совпадение — перенос |
| ≥ 0.55, но без уверенности | **неоднозначно** — решает пользователь в форме предпросмотра (выбор конкретного нарушения или «новое»), никогда не сливается молча |
| < 0.55 у всех | новое нарушение |

При переномеровке (печатный «№» меняется, текст и раздел — нет)
нарушение находится по тексту и **сохраняет свой прежний внутренний
`sys_no`** — печатный номер из нового акта в `sys_no` больше не
переписывается. Для НОВЫХ нарушений `sys_no` тоже больше не берётся из
акта — присваивается свой (`max(sys_no)+1`, `main.py`, внутри
`rsk_import_confirm`). Проверено синтетически (переномеровка + 3
закрытых + 1 новая позиция внутри отменённой транзакции) — подробности
и REQUIRES COORDINATOR DECISION по калибровке порогов —
`docs/RUN_20260925_rsk_checkbox_single_responsible_act_import.md`.

## 6. Предпросмотр ничего не пишет, отмена не оставляет следа в БД

- `rsk_import_preview()` — единственное обращение к БД внутри неё:
  `query_one("select 1 from rsk_act where act_no=%s", ...)` — `SELECT`,
  не запись. Функция сохраняет PDF на диск и вызывает
  `_rsk_build_import_result()` (чистая функция над уже прочитанными из
  БД кандидатами, тоже только чтение) — ни одного `insert`/`update`.
- Запись происходит только в `rsk_import_confirm()`, только внутри
  `run_in_transaction(_do)` — единственная точка входа, требует явного
  POST на `/rsk/import/confirm` с корректным токеном.
- **Отмена** (`<a href="/rsk/import">Отменить, загрузить другой
  файл</a>`) — обычная ссылка, GET-запрос, не вызывает confirm вообще:
  в БД ничего не появляется и не может (не было ни одной записи).

**ПОПРАВКА 25.09.2026** — до этой правки временный PDF-файл на диске
не удалялся при отмене вообще (найдено №3 ниже, было). Теперь:
файл предпросмотра удаляется НЕМЕДЛЕННО, если предпросмотр отклонён
защитами §7 (скан/чужой формат/не распознан номер-дата/0 позиций/
дубликат акта); при обычной отмене (пользователь просто ушёл со
страницы) файл остаётся до следующего визита на `/rsk/import`, который
удаляет из `RSK_UPLOADS_DIR` (не из `.../confirmed/`) все файлы старше
суток (`_rsk_cleanup_abandoned_uploads()`, вызывается в
`rsk_import_page()`) — по возрасту, не по событию, явного сигнала
«отмена» в HTTP нет. PDF **подтверждённого** акта, наоборот, теперь
хранится НАВСЕГДА как первоисточник — переносится (`os.replace`, не
копия) из временной директории в `RSK_UPLOADS_CONFIRMED_DIR` под именем
по номеру акта (`{act_no}.pdf`), `rsk_act.pdf_path` указывает на этот
постоянный путь. До этой правки подтверждённый файл, наоборот,
УДАЛЯЛСЯ сразу после записи (`os.remove(pdf_path)` был и на успешном
пути тоже) — `rsk_act.pdf_path` в БД указывал на уже не существующий
файл, первоисточник физически терялся сразу после импорта. Это тоже
находка №3 ниже, закрыта этой же правкой.

## 7. Жёсткие защиты предпросмотра/подтверждения (координатор, 25.09.2026)

Добавлено после того, как §4 выше показал дыру: скан молча даёт
«0 позиций», подтверждение такого предпросмотра закрыло бы (структурно)
ВСЕ активные нарушения разом (диф видит: 0 позиций в новом акте, значит
все нынешние открытые — «исчезли», то есть сняты).

**На предпросмотре (`rsk_import_preview()`) и повторно на подтверждении
(`rsk_import_confirm()`, защита в глубину — тот же PDF перепарсивается
заново, не доверяет состоянию экрана) — жёсткий отказ, ничего не
пишется, файл удаляется немедленно**, если верно любое из:
- `checks["total_chars_extracted"] < 200` (`RSK_TEXT_LAYER_MIN_CHARS`) —
  «Файл не содержит текстового слоя (скан)...».
- `checks["header_ok"] is False` — сигнатура нумерации колонок
  («1 2 3 4» под заголовком таблицы, см. §2) не найдена ИЛИ найдена не
  в тех координатах, что заданы `BOUNDS` — «Формат акта отличается от
  ожидаемого — нужна настройка парсера».
- номер или дата акта не распознаны — «Не удалось распознать
  номер/дату акта».
- 0 позиций разобрано — «В акте не найдено ни одного замечания».

**Массовое закрытие** — если акт закрывает больше половины сейчас
активных нарушений (`RSK_MASS_CLOSURE_THRESHOLD = 0.5`), подтверждение
требует отдельной явной галочки на экране предпросмотра («Подтверждаю:
акт снимает N из M активных замечаний»); без неё — отказ с показом N/M,
ничего не пишется. Это НЕ жёсткий отказ (файл не удаляется, можно
подтвердить повторно тем же токеном, отметив галочку).

Тесты — `tools/test_rsk_parser.py`: скан (растеризованная страница
реального акта), реальный акт №4183-159 (сверка числа позиций с БД —
152/152), сдвинутый формат таблицы (синтетические координаты — в
контейнере нет библиотеки для генерации PDF с текстовым слоем в
контролируемых координатах, `pypdfium2` — только чтение/растеризация;
ограничение явно оговорено в докстринге теста). Ничего не пишет в БД.

Полный разбор, живая проверка — `docs/RUN_20260925_rsk_act_import_-
safety_guards.md`.
