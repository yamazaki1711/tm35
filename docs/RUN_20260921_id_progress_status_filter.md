# TM-35 — /id-progress: статус-фильтр рядом с «Вкладка» на матрице «Раздел × Этап» (задание координатора 21.09.2026)

## §0 — находка, которая меняет done-критерий 4 задания

Задание утверждало: «справочник `id_form_status` держит девять значений
для большинства вкладок плюс „Не подписаны предыдущие работы" только на
«Труба Сварка»» и требовало живой демонстрации «дропдаун отличается по
вкладкам, назвав «Труба Сварка»».

Проверено живым запросом по ВСЕМ 17 вкладкам (включая `opv`/`n`,
исключённые из `/id-progress`): **все 17 вкладок имеют идентичный список
из 10 статусов**, в одном порядке `display_order`. Статуса «Не подписаны
предыдущие работы» нет нигде в базе.

Причина — это не дефект, а уже принятое и выполненное решение
координатора: `KNOWN_ISSUES.md` §14, «Вопрос 7 — единый справочник
статусов» (реализовано 03.09.2026, за 18 дней до этого задания). Факт на
тот момент был ровно тем, что описывает нынешнее задание — статус
«Не подписаны предыдущие работы» существовал только на 3 вкладках (Труба
Сварка, Скользячки, Обвязка) — координатор явно решил: «статус раздела
единый для всех 15 вкладок ИД», лишний статус удалён (backup снят,
использование в `id_form_entry` проверено — 0 строк). Миграция 031
(09-10.09.2026) добавила «Подписано в карандаше» СРАЗУ ВСЕМ вкладкам
(комментарий в файле: «справочник унифицирован 03.09.2026 (17 вкладок ×
9 значений)»), подняв канонический список до 10 значений — снова
одинаковый везде.

**Вывод**: задание описывает состояние ДО 03.09.2026, устаревшее к
21.09.2026 более чем на две недели. Возвращать особый статус ради
демонстрации значило бы отменить уже принятое и выполненное решение
координатора без нового явного указания — это прямо запрещено правилом
проекта «отрицательный результат окончателен» (переоткрывать закрытый
вопрос нельзя, вернуть в работу может только координатор). **Конкретная
демонстрация «дропдаун отличается по ТЕКСТУ вариантов для одной
вкладки» невозможна честно** — сделано вместо неё (см. §3): дропдаун
явно читает СВОЙ, отдельный набор строк `id_form_status` на каждую
вкладку (разные numeric id у одинаковых по тексту статусов на разных
вкладках — доказательство, что справочник не захардкожен, при том что
сейчас его содержимое намеренно одинаково всюду).

## §1 — реализация

- **Второй `<select name="status">`** в том же `<form class="filter-bar"
  method="get">`, рядом с «Вкладка», `onchange="this.form.submit()"`.
- **Список статусов — из `id_form_status` для ВЫБРАННОЙ вкладки**,
  `order by display_order` (`backend/main.py`, маршрут `/id-progress`):
  ```python
  status_options = query(
      "select id, code, label from id_form_status where tab_id=%s order by display_order",
      (selected_tab_id,),
  ) if selected_tab_id else []
  ```
  `Все` — первый пункт, жёстко в шаблоне (значение `all`, выбран по
  умолчанию — то же правило, что уже действует на `/id-folders`).
  `Без записи о статусе` — последний пункт, значение `none`.
- **Фильтрация строк матрицы** — `compute_id_matrix()` получил параметр
  `status_filter`. Правило «текущий статус раздела» НЕ переизобретено:
  использована та же величина, что матрица уже вычисляла для цвета
  замороженного столбца (`current_color`) — последняя ОТПРАВЛЕННАЯ
  запись `id_form_entry` по `row_id` (без разбивки по `work_type_id`),
  тот же принцип, что `LATEST_ID_FORM_ENTRY_CTE` использует везде в
  проекте для этого понятия. Физически то же значение просто ещё и
  участвует в отборе строк, отдельного запроса не заводилось.
  `status_filter`: `"all"` — без фильтра; `"none"` — разделы вовсе без
  единой записи `id_form_entry`; иначе — `id_form_status.id` (строкой) —
  сравнивается с id, не с текстом, чтобы фильтр не путался, если два
  статуса когда-нибудь совпадут по названию.
- **Валидация на маршруте**: значение `status`, не входящее в `{"all",
  "none"} ∪ {id статусов ЭТОЙ вкладки}`, тихо откатывается на `"all"` —
  id из чужой вкладки не подходит по построению (своя копия строк на
  каждую вкладку), значит и не пройдёт проверку; поведение то же, что
  уже принято на `/id-folders` для некорректного `status`.
- **Ячейки внутри строки не меняются** — фильтр отбирает `rows` до
  построения `cells`, отфильтрованная строка показывает полную недельную
  историю как обычно.
- **Смена вкладки сбрасывает статус на `all`** (JS на `onchange`
  `Вкладка`: `document.getElementById('id-progress-status-select')
  .value='all'` перед `this.form.submit()`) — id статуса с одной вкладки
  ничего не значит на другой (своя копия строк с другими id), переносить
  нельзя.
- **Окно недель переживает обе смены** (§4 задания) — `week_offset`/
  `show_all` продублированы скрытыми `<input>` в той же форме, и
  добавлены в `href` всех навигационных ссылок матрицы (← Раньше / Позже
  → / Показать весь период / Свернуть), которые раньше их не несли.
- **Честное пустое состояние**: если после фильтра строк 0, а до фильтра
  их было больше 0 — сообщение называет конкретный статус и число
  разделов на вкладке без фильтра, а не общую фразу «Разделов нет»
  (которая остаётся для случая, когда на вкладке действительно 0 разделов
  вообще).

## §2 — легенда «3/7»: проверено, что она НЕ является живым числом

Задание просило проверить: «фраза `3/7 — подписано видов работ / всего
видов работ` должна по-прежнему описывать то, что видно после фильтра».
Проверено чтением шаблона: эта строка — **буквальный статический текст**,
без переменной Jinja (`<span class="id-matrix-legend-fraction">3/7 —
подписано видов работ / всего видов работ</span>`), НЕ агрегат уровня
вкладки. Она объясняет формат ячейки внутри строки таблицы («видов работ
подписано / всего видов работ», как в каждой ячейке `{{ c.signed }}/{{
c.total }}»), не итог по всей вкладке. Фильтрация строк не меняет
формат ячейки — эта фраза остаётся верной после фильтра ровно потому,
что никогда не была статистикой, зависящей от набора строк. Оставлена
без изменений — трогать её значило бы чинить то, что не сломано, в этой
задаче; если координатор хотел ЖИВУЮ агрегатную дробь для вкладки —
это отдельная задача (не описанная явно в этом задании), не смешиваю с
текущим фиксом.

## §3 — живая проверка (все числа получены запросом, не подсчётом на глаз)

**Дропдаун — не захардкожен, читает свой набор строк на каждую
вкладку** (доказательство вместо невозможной демонстрации §0):
```
Труба Сварка (tab_id=3):  status_options id = [19, 20, 21, 22, 23, 24, 159, 25, 26, 27]
Изоляция     (tab_id=13): status_options id = [112,113,114,115,116,117,169,118,119,120]
```
Одинаковый ТЕКСТ (namerованием статусов), РАЗНЫЙ id на каждой вкладке —
подтверждает, что список строится запросом `where tab_id=%s`, а не общей
константой.

**Разделы без записи о статусе — по вкладкам** (проверка живым запросом,
`not exists (select 1 from id_form_entry where row_id=r.id)`):
```
ОПН:           98 / 163
ОПН (рсм):    105 / 211
Труба Сварка:  17 / 68
все остальные:  0 (у каждой вкладки все разделы хотя бы раз затронуты)
```

**Для одной вкладки (Труба Сварка) — построчные счётчики по статусу
суммируются в невфильтрованное число строк** (done-критерий 2):
```
есть в эл.виде:            2
не приступали:            25
Первичная проверка РСК:    3
Устранение замечаний 1:    0
Повторная проверка РСК:    0
Устранение замечаний 2:    0
Подписано в карандаше:     0
Подписано:                21
Нет проектного решения:    0
Замечания к площадке:      0
Без записи о статусе:     17
----------------------------
СУММА:                    68  =  68 (невфильтрованное число разделов на вкладке)
```

**Скриншоты** (`/id-progress`, авторизован admin), три ширины
(1366×768, 1920×1080, 2560×1440 — рендер идентичен на всех трёх, тот же
сайтовый `max-width:1360px`):
- оба селекта рядом, состояние по умолчанию (Все / Труба Сварка);
- `status=25` (Подписано) — окрашенные зелёным строки, `week_offset=5`;
- `status=none` (Без записи о статусе) — строки УТ2-Н25/Н25-Н26 и т. п.;
- `status=22` (Устранение замечаний 1, пустой результат) — честное
  сообщение «На этой вкладке нет разделов со статусом «Устранение
  замечаний 1» (68 раздел(ов) всего на вкладке)».

**Переживание окна недель при обеих сменах** (done-критерий 3):
- старт: `?tab_id=3&status=25&week_offset=5` (окно 13.04–19.06.2026);
- смена статуса через реальный `<select>` → `?tab_id=3&status=none&-
  week_offset=5` — окно то же;
- смена вкладки через реальный `<select>` → `?tab_id=13&status=all&-
  week_offset=5` — статус сброшен на `all` (см. §1, почему), окно недель
  то же (`week_offset=5` сохранился).
