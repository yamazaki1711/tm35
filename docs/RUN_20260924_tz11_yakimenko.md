### Б4 — «Стоимость после подписания» убрана, перенос не потребовался

На 24.09.2026 **0 из 21 папок** имеют `amount_smeta_rub` — поле НИКОГДА
не использовалось (проверено прямым SQL до правки). Стоимость всех 21
папки на сегодня целиком определяется `amount_rub` — «Стоимость при
сборке» уже была и остаётся единственным реально работающим входом
(`id_folder_cost() = coalesce(amount_smeta_rub, amount_rub)` — coalesce
никогда не переключался на первую ветку). Условие задания «если
стоимость редактируется ТОЛЬКО в этой секции — перенести» не
выполнилось — стоимость и раньше editable в другом, оставшемся месте.
**Перенос не делал.** Эндпоинт `/api/id-folder/{id}/smeta` удалён вслед
за формой (единственный вызывающий — эта же форма).

**Важно для координатора**: массовый ввод (`/id-folders/bulk-entry`,
отдельная страница, вне периметра этого задания) по-прежнему пишет
`amount_smeta_rub` через свой собственный `/api/id-folder/{id}/bulk` —
если это поле когда-нибудь понадобится заполнить, путь остаётся там, не
исчез совсем, просто не на карточке одной папки.

**Живая проверка** (throwaway-папка id=26, создана/подписана/стоимость
изменена/удалена в одном заходе, откачено полностью):

### Б5 — что могло сломаться и не сломалось

- **«Готово к сборке»** (`signed_not_in_folder`) — считается по статусу
  РАЗДЕЛА (`id_form_status`/`id_form_entry`), не по датам ПАПКИ. Б1/Б2/Б3
  этого числа не касаются вообще — проверено чтением
  `compute_id_folder_stats()`, зависимости нет.
- **Стадия папки** (`id_folder_stage()`/`id_folder_pipe_stage()`,
  колонка «Статус» в списке/CSV, труба) — обе функции уже проверяют
  `ks2_date`/`signed_date` раньше `check_start_date`/`sdo_transfer_date`
  в своей цепочке приоритета, деградируют корректно при отсутствии более
  ранних дат. Ничего не сломалось; единственное следствие — стадии
  «Передана в СДО»/«Проверка» больше не будут заводиться для НОВЫХ папок
  (для уже существующих данные и стадия остаются как были).

## REQUIRES COORDINATOR DECISION

1. **`/id-folders/bulk-entry`** (вне периметра этого задания) продолжает
   писать `signed_date` и `ks2_date` НЕЗАВИСИМО через свой `/bulk`
   эндпоинт — тот же класс расхождения, который карточка папки теперь
   структурно исключает, там по-прежнему возможен. Нужно ли привести
   массовый ввод к тому же «одна дата на обе колонки», что и карточка?
2. **Стадия «Следующая КС-2»** (`ks2_next` — подписана, КС-2 ещё нет, но
   сметная стоимость уже известна) становится структурно недостижимой
   для новых папок — подписание и КС-2 теперь всегда одновременны. На
   24.09.2026 она и без этой правки была пустой (0 папок соответствовали
   условию) — заметный эффект нулевой, но стоит зафиксировать явно, не
   молчать про сужение множества достижимых состояний трубы.
3. **«Последние переходы»** (`/id-folders`, `compute_id_folder_transitions()`)
   будет показывать ДВЕ строки с одинаковой датой («Подписана» и
   «Оформлен КС-2») для каждого будущего слитого сохранения — не
   ошибка, но выглядит избыточно. Схлопнуть в одну строку «Подписана и
   оформлен КС-2» — отдельная, не запрошенная этим заданием правка,
   не делал самовольно.
4. **`amount_smeta_rub`** остаётся в схеме, но у него теперь только один
   путь заполнения (`/id-folders/bulk-entry`) вместо двух — если это
   поле не нужно вовсе, отдельное решение о его судьбе (колонку не
   трогал, «ничего не удалять» из задания).
