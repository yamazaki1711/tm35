# TM-35 — «Качество данных» перестала быть архивом, инвентаризация свежести данных по всем страницам (задание координатора 18.09.2026)

Координатор был прав: `/quality` была архивом одного Excel-импорта, не
проверкой. Задание — исправить эту страницу и проверить остальные на
тот же дефект.

## §1 — подтверждение трёх утверждений задания

Все три утверждения задания проверены против кода и боевой БД,
подтверждаются буквально:

1. **`work.data_quality_flag`/`daily_progress.data_quality_flag`
   пишутся только `import/load_to_postgres.py`.** Ни один веб-маршрут
   их не устанавливает (`grep -n "data_quality_flag\s*=" backend/main.py`
   — 0 совпадений; те же метки в `import/load_to_postgres.py:56,117`,
   часть `on conflict … do update set data_quality_flag = excluded…` —
   офлайн-скрипт импорта, не работающее приложение). Ничем не снимаются
   — ни одного `UPDATE ... data_quality_flag = ...` вне этого скрипта.
   На 18.09.2026: **7 строк `work`** с меткой (все — `updated_at =
   2026-08-29 03:47:03 UTC`, один и тот же прогон импорта; самая старая
   из семи — `2026-08-29 00:17:41`, тоже 29.08), **0 строк
   `daily_progress`** с меткой.
2. **`import_unresolved_cell` заполняется только парсерами импорта.**
   `resolved` — колонка есть (`migrations/001_init.sql:398`, default
   `false`), интерфейса, который мог бы её установить в `true`, нет
   нигде (`grep -rn "resolved\s*=\s*true\|update import_unresolved_cell"
   backend/main.py import/*.py` — 0 совпадений). На 18.09.2026 таблица
   **пуста — 0 строк** (не выборка, полный `select count(*)`).
3. **С 01.09.2026 Excel не источник.** `daily_progress` по `source`:
   `excel_import` — 1146 строк, последняя `created_at` **2026-08-29
   00:17:31 UTC**; `web_form` — 431 строка, последняя **2026-09-18
   03:14:44 UTC** (сегодня); `schedule_derived` — 91 строка, разовая
   (см. ниже). Ни одной строки `excel_import` с `created_at` после
   01.09.2026 — **0**, прямым запросом.

Вывод: страница физически не могла показать ни один дефект новее
29.08.2026 и не могла перестать показывать уже исправленный — три метки
застыли в момент последнего прогона импорта, интерфейса ни писать
(кроме импорта), ни снимать их не существует.

## §2 — `/quality` перестроена: живые проверки вместо архива

`backend/main.py`: новая функция `compute_quality_checks()` заменяет
оба раздела, читавших метки, двенадцатью проверками, вычисляемыми SQL
заново при каждом заходе — против таблиц, которые действующие формы
меняют прямо сейчас:

**СМР** (5): запись вне директивного периода 01.09–28.11.2026 (835,
из них 216 через веб-форму — показаны первыми, остальные 594+25 —
исходный график/расчёт, не дефект, см. комментарий в коде); факт людей
превышает план на 3+ человека за день (10, порог назван прямо в
заголовке); «% выполнения» уменьшился по сравнению с предыдущей
записью по той же работе (1); работа получает факт после 100% (1); нет
плановых сроков ни в `current_schedule`, ни в `baseline_schedule` (25).

**ИД** (5): запись раздела без вида работ там, где вкладка виды работ
поддерживает (24 — было 23 на 14-15.09.2026 в `KNOWN_ISSUES.md` §41,
+1 новая запись за три дня, естественный дрейф); дата статуса раздела в
будущем (0); невозможная последовательность дат папки — КС-2 раньше
подписания или подписание раньше начала проверки (0); КС-2 оформлен без
стоимости (0); папка без единого раздела (0).

**РСК** (2): нарушение отмечено «Устранено», но всё ещё в последнем
акте (**15** — тот самый интересный случай, который прошлая задача
специально не прятала, тайл «Устранено» и структурное закрытие акта —
разные слои); отработка ссылается на нарушение вне всех актов (0).

Каждая строка находки — ссылка на запись: СМР → `/shift?date=…&q=<шифр>
&all=1` (открывает нужный день и работу сразу), ИД-папки →
`/id-folders/{id}`, РСК → `/rsk/processing?sys_no=<№>`. Для находок
уровня раздела ИД (нет привязки к одной странице-карточке) — ссылка на
`/id-progress`, лучшее из существующего.

Раздел «Нераспознанные ячейки» переехал вниз под заголовок «— разовый
архив импорта Excel» с числом и датой прямо в заголовке (не отдельной
подписью — CLAUDE.md §7 запрещает пояснительные абзацы между
заголовком и содержимым, дата поэтому в самом `<h3>`); при 0 строк
заголовок честно говорит «дата не восстановима — таблица пуста», не
подставляет правдоподобную дату.

`compute_quality_checks()` — общая функция для `/quality` и тизера
«Качество данных» на `/data` (правило проекта «хаб вызывает ту же
функцию», 31.08.2026) — было `count(*) from work where
data_quality_flag=...`, стало `sum(c["total"] for c in
compute_quality_checks())` = **911** на 18.09.2026.

**Живьём пойманное и исправленное по пути**: без ограничения показа
браузер реально подвисал (таймаут рендера CDP) на 835 строках одной
проверки при широком окне. Добавлен предел показа 150 строк на
проверку — заголовок и тизер `/data` считают **полное** число
(`c["total"]`), обрезан только рендер, с явной пометкой «показаны
первые N из M — список не сокращён в базе».

## §3 — инвентаризация всех страниц

`docs/DATA_FRESHNESS_INVENTORY_2026-09-18.md` — 45 строк (44 маршрута +
`/id-folders/{folder_id}`, добавлена вручную как слишком важная, чтобы
пропустить), только чтение, ни одна строка БД не менялась.

**Главная находка, не про `/quality` вообще**: тайл «Всего по
контракту, ₽» на `/dashboard` и `/id-folders` читается из хардкод-
константы `ID_FOLDER_CONTRACT_TOTAL = 4078191380.98` в `main.py:5165`,

`ИКС_/ДУ/5/06122022`, стороны, дата, статус `ACTIVE`) и хранит то же
число, но не читается приложением вовсе. Тот же класс дрейфа схемы, что
`KNOWN_ISSUES.md` §52 уже описывает для других таблиц — константа и
таблица сейчас совпадают числом, но правка одной не затронет другую.

**Вторая находка**: несколько ключевых цифр (`get_remaining_effort()`,
`get_evm_data()`, `get_today_data()` — трудоёмкость по проекту) считаются
живым SQL, но по `daily_progress` с `source='excel_import'` — набору,
который не пополнялся с 29.08.2026. Механизм живой (честно пересчитывает
каждый раз), исходный срез — заморожен. Затрагивает `/calculator`,
`/status`, `/dashboard`, `/today`, `/critical`, `/`, `/data`.

Дальше — обычный набор: `baseline_schedule` (**149** строк, не 146, как
называет задание — расхождение не расследовано, вне периметра;
легитимный разовый импорт, как задание и предполагало), `ssr_norm`/
`gesn_norm` (373/12625, справочники), структурная конфигурация формы ИД
(`id_form_tab`/`id_form_work_type`/`id_form_responsible` — тот же риск
перезаписи, что уже в `KNOWN_ISSUES.md` §43), устаревшая `id_package`.

Полный разбор, таблица по всем 45 страницам, свидетельства (файл:строка
на каждую классификацию) — в самом файле инвентаризации.

## Требует решения координатора

- **`ID_FOLDER_CONTRACT_TOTAL` (хардкод) vs таблица `contract`** — числа
  сейчас совпадают, но правка одного не затронет другой; перевести тайл
  на чтение из `contract` — отдельная маленькая задача, не делал без

  которые сейчас нигде не показаны).
- **Трудоёмкость считается по замороженному с 29.08.2026 срезу**
  (`source='excel_import'`) — новая работа или пересмотр объёма после
  этой даты никогда не попадёт в расчёт без повторного прогона
  `import/load_to_postgres.py` или нового способа ввода трудоёмкости,
  которого сейчас в приложении нет. Затрагивает `/calculator`, `/status`,
  `/dashboard`, `/today`, `/critical`.
- `baseline_schedule` — **149** строк по факту, не 146 (как называет
  задание и как считалось раньше) — расхождение не расследовано.
- `id_report_group` (основа «Графика ИД») — происхождение не найдено ни
  в `main.py`, ни в `import/`, похоже на прямой ручной SQL; направление
  и так на паузе координатора с 11.09.2026, не копал глубже.
- `app_setting['directive_start']` редактируется только прямым SQL —
  `directive_deadline` рядом уже имеет форму на `/settings`,
  `directive_start` нет.
- `/losses` — не расследовалась внутри этой инвентаризации (уже
  зафиксирована как недостижимая ни из одного меню, `KNOWN_ISSUES.md`
