## Шаг 4 — откат данных

**Находка перед откатом:** 2 реальные записи ПТО с сегодняшнего утра
(`work_id` 106 и 186, дата 2026-08-01, факт людей 3 и 4,
`audit_log.action='shift_cell_edit'`, ~10:08-10:09 по Владивостоку) —
физически отсутствуют в бэкапе `tm35_backup_before_smr_reload_310826.sql`
(он снят раньше). Координатор подтвердил: сохранить обе поверх отката.

**Безопасность:** снят дополнительный бэкап текущего (до отката данных)
состояния — `import/rollback_010926/tm35_backup_before_data_rollback_010926.sql`
(`work`=171, `daily_progress`=1502, `baseline_schedule`=149) — на случай,
если сам откат придётся откатывать.

**Обнаруженный и обойдённый риск.** Первая попытка написать restore
на чистом Python (regex-разбор дампа) молча теряла строки —
многострочные текстовые поля (`comment`/`name` с переносами) ломали
построчный разбор; `work` парсился как 103-168 из 169. Не стал
дотягивать регэксп руками — вместо этого дамп загружен через
собственный SQL-парсер Postgres в отдельную схему `restore_stage`
(`psql -f`, копии `public.→restore_stage.`), и сама реставрация сделана
как обычный SQL (`UPDATE`/`DELETE`/`INSERT SELECT`) — без риска молча
потерять строку. Схема `restore_stage` дропнута после успешной
проверки числа строк.

**Порядок восстановления** (одна транзакция, `import/rollback_010926/do_restore.sql`):
1. `daily_progress` — удалены и заново вставлены ТОЛЬКО строки
   `source='excel_import'` (1146 из бэкапа). `web_form` (54, включая 2
   сегодняшние) и `schedule_derived` (91) не тронуты вообще — не входят
   ни в удаление, ни во вставку.
2. `baseline_schedule` — таблица целиком выводится из Excel-импорта
   (второй источник записи не существует, см. `SMR_REBUILD_2026-08-29.md`
   §3) — безопасная полная замена: удалено 149, вставлено 148 из бэкапа.
3. `work` — удалены 2 работы, заведённые вчерашним импортом
   (`TM35-AUX-151`, `TM35-AUX-152`) — предварительно проверено по всем
   9 таблицам с FK на `work.id` (`baseline_schedule`, `blocker`,
   `current_schedule`, `daily_progress`, `downtime_cause`,
   `equipment_work_link`, `material_work_link`, `prescription`,
   `resource_reallocation`, `simple_form_hidden`) — 0 ссылок на эти 2
   id ни в одной, кроме уже очищенных `daily_progress`/`baseline_schedule`.
4. `work` — у оставшихся 169 работ (id не менялись импортом ни разу,
   только столбцы) столбцы обновлены `UPDATE ... FROM restore_stage.work`
   обратно к значениям бэкапа — не `DELETE`+`INSERT`, чтобы не задеть
   FK ни из одной из 9 таблиц выше.
