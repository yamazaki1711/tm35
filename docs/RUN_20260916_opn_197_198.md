# TM-35 — добавление разделов ОПн197/ОПн198 на вкладку «ОПН (рсм)», 16.09.2026

Находка координатора 15.09.2026: при подготовке исходного xlsx
пропущены два раздела вкладки «ОПН (рсм)». Задание — добавить их во всю
систему (матрица `/id-progress`, каскад `/id-entry`, все счётчики
разделов), не создавая записей `id_form_entry`.

## §1 — проверка перед записью (это могла быть не вставка)

1. `id_form_tab` для «ОПН (рсм)»: `id=2`, `code='opn_rsm'`,
   `has_section_level=true`.
2. 10 хвостовых строк вкладки прочитаны verbatim — видимая метка живёт
   в `section_label` (буквально `ОПн15`…`ОПн226`, строчная «н»
   подтверждена), `construction_label`/`foundation_label` у всех строк
   этой вкладки `NULL`, `note` тоже `NULL` до этой миграции.
   `source_row` — целое, не `NULL` ни у одной из 209 строк.
3. `source_row` — плотная последовательность 1..209 (209 строк, ровно
   столько же). Это НЕ буквальный номер строки исходного xlsx: местами
   числовой порядок лейбла нарушен (например `ОПн57` стоит на позиции
   33, раньше `ОПн48` на позиции 34) — так было в источнике, не трогал
   ничего, кроме необходимого хвоста. Между `ОПн196` (`source_row=100`)
   и `ОПн199` (`source_row=101`) — оба соседних целых, свободного номера
   нет.
4. **Поиск ОПн197/ОПн198 по всей системе** (точное совпадение и
   варианты написания/регистра, плюс просто «197»/«198» в любом из трёх
   лейбл-полей любой вкладки) — бэйр-лейблов `ОПн197`/`ОПн198` нет
   нигде. Найдены **похожие, но не те же** записи на вкладке
   «Скользячки» (`tab_id=4`): `Т1-Опн197`, `Т1-Опн198`, `Т2-Опн197`,
   `Т2-Опн198` — составные метки с собственной нумерацией по трубам
   (Т1/Т2), число 197/198 у неё уже дважды повторяется ВНУТРИ самой
   «Скользячки» между разными трубами — совпадение числа, не тот же
   раздел и не перенос. Продолжил как вставку.

## §2 — миграция

`migrations/036_id_opn_rsm_197_198.sql`. Раздвинут ТОЛЬКО хвост вкладки
`tab_id=2` (`source_row >= 101`, +2), два новых `id_form_row` вставлены
в освободившиеся 101/102 — встают строго между `ОПн196` и `ОПн199`.
`construction_label`/`foundation_label` — `NULL`, как у соседей.
`note` — «Раздел отсутствовал в исходном xlsx, добавлен по указанию
координатора от 15.09.2026». Никакого `id_form_entry` не создано.
Идемпотентно (`do $$ if not exists (... section_label='ОПн197') $$`) —
прогнан дважды, второй прогон no-op, дублей и ошибок нет.

**Бэкап перед записью** — `pg_dump -U kat_admin -d tm35 --data-only -t
id_form_row`, сохранён в
`import/opn_rsm_197_198_20260916/tm35_backup_before_opn_197_198_20260916.sql`
(в git, не только на сервере).

## §4 — риск повторного импорта

`import/id_kontur/{reload_id_form_v2,reload_id_rows_v3,load_id_form}.py`
проверены на `truncate`/`delete` над `id_form_row`:

- `reload_id_form_v2.py` — безусловный `truncate ... id_form_row ...
  cascade`, без единой защитной проверки. Самый опасный: перезапуск
  сегодня стёр бы оба новых раздела (и вообще всё, что накопилось с
  27.08.2026 — источник вкладок там же — замороженный
  `/tmp/old_rows_by_tab.json`).
- `reload_id_rows_v3.py` — тоже `truncate id_form_row cascade`, но
  ПЕРЕД этим — стоп-проверка "не truncate вслепую", если
  `id_form_entry`/`id_form_block` не пусты. Сегодня в системе тысячи
  реальных записей — скрипт откажется бежать сам, но это побочная,
  не целевая защита новых разделов.
- `load_id_form.py` — только `insert`, не в списке риска.

Запись внесена в `KNOWN_ISSUES.md`, §43. Сами скрипты не менял — не
входило в периметр задания.
