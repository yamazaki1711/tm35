# TM-35 — РСК: три правки (25.09.2026) — выравнивание переключателя, один ответственный отдел, восстановление и переработка загрузки акта

Одна ветка задания, три части. Все проверены живьём на тестовых копиях

## Часть 1 — выравнивание переключателя «Ответственный»

**Причина (не разная разметка).** Все элементы группы «ПТО/ДПР/строй-
площадка/Лаборатория» — байт-в-байт одинаковый HTML. Разъезд по
вертикали (8px) давало глобальное правило `style.css`:
```
.form-box label { display:block; margin-top:1rem }
.form-box label:first-child { margin-top:0 }
```
Локальное правило `.rsk-checkbox-row label { flex-direction:row;
align-items:center; gap:.4rem }` не переопределяло ни `display`, ни
`margin` — оба свойства без `display:flex` на самом элементе ничего не
делают, поэтому `display:block`+`margin-top` из общего правила
продолжали действовать. Первый элемент в `<div>` — единственный,
попадающий под `:first-child`, получал `margin-top:0`; остальные три —
`margin-top:16px` от того же правила. Проверено `getBoundingClientRect`
ДО правки: 1006.9px vs 1014.9px (три элемента).

**Исправление**: `.rsk-checkbox-row label { display:inline-flex;
align-items:center; gap:.4rem; margin:0; ... }` — явно нейтрализует оба
свойства. Тот же класс дефекта проверен и у `.rsk-standalone-check`/
`.rsk-comment-block label` (единственные другие места в приложении,
попадающие под `.form-box label`, отдельные проверены — тоже теряют
`display:flex` из-за той же специфичности, но эффекта не видно: группа
из одного элемента визуально не с чем сравнивать) — НЕ тронуты, за
пределами буквального запроса «группы чекбоксов» и без видимого дефекта.
Других мест с ТОЧНО такой же конструкцией (`{% for %}`-цикл, оборачивающий
несколько `<label><input type=checkbox>...</label>` внутри `.form-box`)
в приложении не нашлось (`gantt.html`/`shift.html` — одиночные
переключатели вне `.form-box`; `id_grafik_category_mapping.html` —
чекбоксы в ячейках таблицы, без обёртки `<label>`).

**Live-проверка** (`getBoundingClientRect`, все 5 пунктов после
поправки 2 ниже — переключатель уже радио, не чекбокс): координаты Y
центра — 1007.375px у всех пяти без исключения, разброс 0.0px (порог
задания — 1px).

### c) Отождествление — было неверно, теперь по тексту+разделу

**Было**: `rsk_violation.sys_no unique`, upsert `on conflict (sys_no) do
update` — идентичность нарушения между актами буквально равнялась
печатному «№» из PDF. Задокументировано так намеренно 06.09.2026
(«Нарушение — сквозная сущность по системному номеру РСК»,
`docs/RSK_ACT_PDF_IMPORT_2026-09-06.md`) — не баг по недосмотру,
предположение, не проверенное на втором акте (второго акта не было).
Координатор сегодня явно скорректировал модель: № РСК может меняться,
матчинг по номеру ненадёжен.

**Стало** — `_rsk_match_new_act()`/`_rsk_build_import_result()`
(`main.py`): похожесть нормализованного текста (`norm_literal` —
lower+collapse whitespace, из `grafik_matching.py`, не новая функция) c
разделом (`control_section`) как жёстким предфильтром;
`difflib.SequenceMatcher`. Три порога:
- **≥0.97** — почти точное совпадение, переносится сразу, без проверки
  отрыва от других кандидатов;
- **≥0.80 И отрыв ≥0.08** от следующего кандидата той же записи —
  уверенное совпадение;
- иначе, если кандидаты вообще есть (≥0.55) — **неоднозначно**, решает
  пользователь в форме предпросмотра (выпадающий список: один из
  кандидатов или «новое»), никогда не сливается молча;
- кандидатов нет вовсе (<0.55 у всех) — новое нарушение.

Жадный алгоритм: все пары (запись, кандидат) сортируются по убыванию
похожести, разбираются по одной, запись и нарушение занимаются
НАВСЕГДА при первом совпадении. Порог 0.97 понадобился по факту живой
проверки (см. §5) — без него margin-проверка ошибочно считала
неоднозначными 53 из 152 позиций при повторной загрузке ТОГО ЖЕ акта:
несколько нарушений одного участка используют один и тот же шаблонный
текст («Участок УТ2-УТ3... бетонированию ростверк...»), и у настоящего
совпадения (100%) находился «конкурент» на 96-98% — отрыв меньше
0.08, хотя сама пара уже безальтернативно точна.

`rsk_violation.sys_no` перестаёт перепечатываться из акта для уже
известных нарушений (при совпадении — не трогается вовсе) и больше не
берётся из акта для новых — присваивается свой, `max(sys_no)+1`,
однажды и навсегда.

**`rsk_processing` и так была на `violation_id`** (миграция 024,
06.09.2026) — проверено в коде, часть задания «if processing keyed to
act_item — fix it» не применилась, чинить было нечего. Единственный
реальный риск был не в внешнем ключе `rsk_processing`, а в том, ЧТО
именно раньше становилось `violation_id` при повторном импорте
(см. выше) — при переномеровке старый алгоритм создал бы НОВУЮ
`rsk_violation` (или того хуже — приписал бы данные не той, если новый
номер акта случайно совпал с чужим существующим sys_no), осиротив
`rsk_processing` старой записи. Новый алгоритм этого не допускает —
доказано синтетическим тестом (§5).

### b) Загрузка, дифф-предпросмотр, отклонение дублей

Тот же двухшаговый поток (`/rsk/import` → предпросмотр → `/rsk/import/-
confirm` → запись), метод разбора PDF не менялся (`rsk_parser.py`,
координатный метод по `page.rects`, не `extract_tables()` — не
трогалось, это отдельная, уже проверенная часть, см.
`docs/RSK_ACT_PDF_IMPORT_2026-09-06.md`).

- **Дубликат акта** — было `on conflict (act_no) do update` (тихо
  перезаписывал бы дату/итог), стало явный отказ: проверка `exists
  (select 1 from rsk_act where act_no=...)` и в предпросмотре
  (информационно, банер), и в `/confirm` (реальный барьер — второй раз,
  на случай прямого POST мимо экрана). Ничего не пишется.
- **Неоднозначные соответствия** — `/rsk/import/confirm` стал `async`,
  читает `resolve_<индекс>` из формы для каждой неоднозначной позиции
  (`<select>` в предпросмотре: конкретное нарушение или «новое»). Не
  все разрешены — форма перерисовывается с ошибкой, ничего не
  записывается; уже выбранные решения не текут дальше в сохранённом
  виде между попытками — они просто перестают быть неоднозначными и
  показываются в «перенесено»/«изменили формулировку» на следующей же
  перерисовке (или остаются на экране повторно, если решения не было).
- **Конфликт «Устранено», но снова в акте** (п. d задания) — импорт
  НИКОГДА не писал и не пишет `rsk_processing` (слой 2 не тронут ни
  строкой), поэтому «не менять флаг автоматически» выполняется самим
  фактом, что писать было и не должно; добавлено только отображение —
  предпросмотр (баннер со списком №) и итоговое сообщение после записи.
- Все производные (реестр, фильтр «Снятые»/«Активные», тайлы «Обзора
  РСК», связи с ИД) уже шли через `rsk_violation_is_removed()`
  (закреплено 24.09.2026) — этот заход не вводит вторую логику «снято»,
  только чинит, ЧТО становится `violation_id` при записи.
