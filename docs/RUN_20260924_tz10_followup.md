# TM-35 — поправка к ТЗ №10 (24.09.2026): /gantt без конфликта с решением координатора, VAT закрыт, РСК «Снятые» подтверждено

Три пункта поверх коммита `922a45a`. Явное правило координатора для этого
захода: «fix the root cause» НЕ равно разрешению отменять
документированное решение координатора — если исправление конфликтует с
решением, чинить БЕЗ конфликта или выносить в REQUIRES COORDINATOR
DECISION, никогда не утверждать, что задание распорядилось тем, чего
оно не говорило.

## Пункт 1 — `/gantt`: весь директивный период вместо точки-дефолта

### Что было неверно в заходе 23.09.2026

Прошлая правка заменила дефолт «начало окна отображения» (01.08.2026)
на «сегодня−7» и написала в run log и `KNOWN_ISSUES.md`, что это
сделано «по прямому указанию» задания «fix the root cause». **Это
было неверно** — задание просило исправить первопричину, не давало
разрешения отменять решение координатора от 01.09.2026. Обе
формулировки исправлены (см. правки в `docs/RUN_20260924_tz10_-
yakimenko.md` и `KNOWN_ISSUES.md` §63 в этом же коммите).

### Настоящее исправление — без конфликта

Дефолт больше не выбирает ТОЧКУ внутри директивного периода (ни
«начало окна», ни «сегодня−7» — обе версии были одним и тем же классом
ошибки). Вместо этого `/gantt` по умолчанию показывает **весь
директивный период целиком**:

- `_gantt_default_range()` (новая функция, `main.py`) читает
  `get_directive_start()`/`get_directive_deadline()` (существующие
  настройки `app_setting['directive_start']`/`['directive_deadline']`)
  — на 24.09.2026 это **01.08.2026 и 28.11.2026** (не 01.09.2026, как
  написано в тексте задания буквально — прочитано из настроек, а не
  захардкожено, ровно как задание и просило; если бы directive_start
  когда-нибудь изменили на 01.09 прямым `UPDATE app_setting`, код
  подхватит это без деплоя).
- Диапазон расширяется, если у какой-то работы плановый срок
  (`current_schedule.current_start`/`current_finish` — то же поле, что
  пишут форма «Сроки» на `/gantt` и ввод факта на `/shift`) выходит за
  эти границы: `min(directive_start, min(current_start), сегодня)` …
  `max(directive_deadline, max(current_finish), сегодня)`.
- **Сознательно НЕ используется `daily_progress.date`** для расширения:
  в этой таблице есть записи с 18.06.2026 (проверено — `min(date) =
  2026-06-18`), а решение координатора от 29.08.2026 прямо говорит
  «данные за июнь-июль не трогаются, просто не показываются здесь».
  Включение daily_progress в расчёт диапазона вернуло бы эти данные на
  экран без нового явного указания — второй конфликт с решением
  координатора, которого это исправление специально избегает.
- Сегодняшняя дата всегда входит в диапазон по построению — баннер
  `#gantt-today-note` от 23.09.2026 убран, ему больше не от чего
  сработать.
- Явный `start`/`days` (клики «пред./след.», выбор «14/30/45/60 дней»,
  кнопка «Сегодня») по-прежнему работают как раньше — ограничение 7-90
  дней и зажатие в границы диапазона остались, но теперь границы —
  расширяемые `_gantt_default_range()`, а не только настроечные даты.
- Фронтенд (`gantt.html`): страница больше не шлёт `start`/`days` в
  первом запросе вовсе — оба поля `state.start`/`state.days` начинаются
  как `null`, и `/api/gantt` сам решает, что показать. После первой
  отрисовки JS один раз прокручивает таблицу так, чтобы сегодняшняя
  колонка была примерно по центру видимой области — прокрутка вбок для
  более ранних дат остаётся доступной без смены фильтров (это уже
  разрешённое исключение CLAUDE.md §7 для этой страницы). Добавлен
  пункт «Весь период» в список «дней» — переключает состояние обратно
  на `null`/`null`, тот же путь, что и первая загрузка.

### Доказательство первопричины (по требованию задания)

Проверено заново: в предыдущем заходе (23.09.2026) тестовая работа с
фактом на 24.09.2026 **не была видна** при открытии `/gantt` без
параметров, потому что тогдашний дефолт («начало окна отображения»,
01.08.2026) показывал срез 01.08–30.08.2026 — 24.09 физически не
попадало в эти 30 дней. Если бы страница по умолчанию показывала ВЕСЬ
диапазон 01.08–28.11 (не 30-дневный срез внутри него), эта же запись
была бы видна без единого клика — то есть причиной было именно то,
КАКОЙ СРЕЗ показан по умолчанию, а не то, что данные не пишутся, не
кешируются неверно или теряются в фильтрах. Отдельно перепроверены
кандидаты из напоминания задания: «Есть факт» (чекбокс по умолчанию
снят, не участвует), сортировка/пагинация списка работ (строки не
фильтруются по датам вовсе), закешированный запрос (каждый `/api/gantt`
— свежий SQL, проверено логами), клиентский кеш браузера (`fetch` без
кеш-заголовков, каждый вызов — сетевой запрос) — ни один не
воспроизвёлся.

**Живая проверка после исправления**: создана тестовая работа
`TM35-MAIN-113` со сроком 25–27.08.2026 (внутри 01.08–28.11) и вторая
`TM35-MAIN-114` со сроком 05–07.12.2026 (**вне** 01.08–28.11) —
`/api/gantt` без параметров сразу же вернул диапазон **01.08.2026 …
07.12.2026** (граница расширилась под вторую работу), обе работы видны
в ответе с верными полями (`current_start`/`current_finish`,
`critical`). Скриншоты — `docs/screenshots_20260924_tz10_followup/`
(`followup_gantt_default.png` — общий вид с диапазоном в статусной
строке; `followup_gantt_outside_work.png` — обе тестовые работы в
списке, TM35-MAIN-113 подсвечена красным шифром как просроченная).
Обе работы и их `current_schedule`/`audit_log` записи удалены после
проверки (id 2633, 2634) — подтверждено прямым SQL: 0 строк в
`work`/`current_schedule`/`daily_progress`/`audit_log` по этим id,
`/api/gantt` их больше не отдаёт, диапазон вернулся к «01.08.2026 …
28.11.2026».

Дополнительно проверено вживую в браузере: «← пред.»/«след. →»
задизаблены при дефолтном «Весь период» (некуда идти дальше — уже
показано всё), выбор «30 дней» сужает диапазон и включает кнопки,
«Весь период» из списка возвращает полный диапазон, «Сегодня»
по-прежнему даёт узкое окно ±около текущей даты (30 дней) — три разных,
осмысленных режима, не один смешанный.

## Пункт 3 — РСК «Снятые»: подтверждено, без изменений кода

**ПОПРАВКА 24.09.2026 (тот же день, третье обращение координатора) —
вывод ниже был неверным, оставлен для истории, не удалён.** Пункты 1 и
2 (список ниже) сами по себе верны — дропдаун не задизаблен, пустое
состояние честное. Ошибка была в САМОМ определении «снято»: этот заход
проверял только СТРУКТУРНОЕ закрытие (`rsk_violation.is_active=false`,
отсутствие в следующем акте) и, найдя его нулём при одном акте, объявил
«Найдено: 0» честным результатом. Это была симптом-проверка, не
проверка полноты определения — реестр отдельно хранит ВТОРОЙ,
независимый признак снятия («Устранено», `rsk_processing.resolved`,
слой 2 формы отработки), и на 24.09.2026 таким признаком отмечены **16
нарушений** («да» или дата снятия в столбце «Устранено»), которые фильтр
«Снятые» не находил, потому что определение не заглядывало во второй
слой вовсе. Полный разбор, живая проверка и правка — см.
`docs/RUN_20260924_rsk_removed_definition_fix.md`.

Исходный (неполный) вывод этого захода — ниже, без изменений:

Проверено заново по обоим требованиям задания:
1. **Пункт «Снятые» не задизаблен и не скрыт** при нулевом счёте —
   `rsk_registry.html` рендерит все три `<option>` (Активные/Снятые/Все)
   статически, без каких-либо условий на количество найденных записей;
   `disabled`-атрибута нет ни у одного из них. Выбирается и работает
   одинаково независимо от результата.
2. **Пустой результат — обычное пустое состояние**: в
   `rsk_registry.html` нет `{% else %}`-ветки с текстом для таблицы
   вовсе — при `rows` пустом просто не рендерится ни одной строки
   `<tbody>`, никакого дополнительного текста сверх того, что уже видно
   всегда («Найдено: {{ total }}» над таблицей — обычный счётчик, не
   специальная надпись под этот случай).

Оба требования уже выполнялись до этого захода — правок в код не
потребовалось **для них**; правка всё же понадобилась, но в другом
месте (определение «снято»), см. поправку выше.

**Акт**: в `rsk_act` по-прежнему ровно одна строка — **№4183-159 от
11.08.2026**. Закрытых **структурно** нарушений
(`rsk_violation.is_active=false`) — по-прежнему **0**, это само по себе
верно и остаётся так до второго акта. Ошибкой было считать, что
структурное закрытие — единственный способ нарушению стать «снятым»
для реестра; после поправки 24.09.2026 «Снятые» = структурно ИЛИ
«Устранено» (слой 2) — см. `docs/RUN_20260924_rsk_removed_definition_fix.md`.
