# ТМ-35 Мониторинг — оптимальный проект (v1.1, синтез ТЗ v0.1 + решения координатора)

Статус: рабочая версия для внедрения. Отменяет v1.0 этого документа
(15.08.2026, тот же день) — в части ежедневного ввода факта: v1.0 полностью
исключал веб-форму из MVP, v1.1 возвращает её как опциональный второй канал.
Причина правки — уточнение координатора: право выбора инструмента ввода
остаётся за сотрудником ИКС, а не решается заранее в его отсутствие.
Также заменяет собой ранний «вердикт комитета» — тот был построен на
неполных вводных (не видел ТЗ v0.1) и в части периметра (Excel навсегда,
без веб-форм вообще, без симуляции) был неверен.

Источник истины по содержанию системы — `ТЗ_ТМ-35.odt` v0.1. Этот документ
корректирует его по трём пунктам, где решение координатора требует
изменить план ТЗ, и оставляет всё остальное как проектную основу.

---

## Что меняется относительно ТЗ v0.1 — и почему

| Пункт ТЗ v0.1 | Решение координатора | Обоснование |
|---|---|---|
| Telegram-бот — открытый вопрос (п. 27.11) | **Закрыт безусловно, не рассматривается** | Telegram заблокирован в РФ. Это не подлежит обсуждению с заказчиком — исключается на уровне архитектуры, не выносится как опция. |
| Модуль симуляции («Дата→люди», «Люди→дата») — часть MVP | **Переносится во 2-ю итерацию** | Сложный расчётный движок не должен блокировать запуск базового план/факт-дашборда. Формулы и схема БД (`scenario`, `scenario_result`) фиксируются в ТЗ как задел, но не реализуются в первом релизе. |
| Инфраструктура — вопрос "существующий VPS или отдельный" | **Решено: существующий VPS**, поддомен `tm.asd-kontur.ru`, отдельная БД `tm35`, изоляция от `bi.asd-kontur.ru` | Экономия ресурсов, более быстрый запуск — соответствует и рекомендации самого ТЗ при выполнении условий изоляции. |
| Роли Планёр/Исполнитель — веб-формы ежедневного ввода | **Уточнено (v1.1)**: Excel остаётся основным и обязательным каналом — сотрудник ИКС не обязан ничего менять. Но поскольку БД и API создаются под импорт, простая веб-форма ежедневного факта добавляется в MVP как **второй, опциональный канал** для той же модели данных (`daily_progress`, поле `source` = `excel_import` / `web_form`). Инженер сам решает, каким пользоваться; при конфликте (оба канала заполнены на одну дату/работу) побеждает более поздняя по времени запись, обе версии остаются в журнале изменений. | Право выбора инструмента — за человеком, который реально вводит данные; это снижает риск отказа от системы. Стоимость формы поверх уже спроектированной модели — небольшая инкрементальная работа, не отдельный архитектурный пласт. |

Всё остальное содержание ТЗ v0.1 (справочник работ с кодами по источникам,
статусная модель, Baseline/Current Plan/Forecast, реестр ограничений с
закрытым справочником причин, реестр субподрядчиков, реестр материалов,
структура дашбордов, требования к миграции) принимается как основа
проектирования без изменений.

## Периметр MVP (первая итерация)

**Входит:**
1. Единый справочник работ с кодами (`TM35-MAIN-001`, `TM35-IKS-001`,
   `TM35-RSK-001`, `TM35-AUX-001`) и полным набором атрибутов из ТЗ
   (источник, участок/локация, тип работы, ед. изм., плановый объём, вес
   для прогресса, тип исполнителя, ответственный, статус, критичность).
2. Статусная модель из 9 состояний (Не начата → ... → Закрыта / Отменена).
3. Разделение Baseline / Current Plan / Forecast с журналом изменений
   базового графика (кто, когда, почему поменял).
4. Ежедневный факт по каждой активной работе (план/факт численности, часы,
   потерянные часы, объём за день, накопленный %, статус, причина
   отклонения). **Два равноправных канала ввода одной и той же модели
   данных**: batch-импорт Excel (основной, обязательный) и простая веб-форма
   (опциональный второй канал, роль Исполнитель). Оба пишут в
   `daily_progress`, поле `source` фиксирует происхождение; конфликт
   разрешается по последней по времени записи, история — в журнале
   изменений.
5. Переброска людей между работами (донор/реципиент/причина/влияние).
6. Учёт вспомогательных работ и их доли в общем ресурсе.
7. Реестр ограничений (материал/поставка/техника/ГСМ/погода/фронт/проектное
   решение/субподряд/договор/оплата/приёмка/последовательность/вспом.
   работы) с закрытым справочником причин простоя (WEATHER_RAIN,
   FUEL_MISSING, SUBCONTRACT_MISSING и т.д. — полный список из ТЗ).
8. Ресурсный пул по датам (доступно/вышло/направлено на основные/вспом./
   замечания/простой/дефицит) — на первом этапе без специализаций
   (монтажники/сварщики и т.д. — это явно помечено в ТЗ как второй этап).
9. Реестр субподрядчиков (статус договора, готовности, влияние на график) —
   с предзаполнением известных на сегодня блокеров (сорванная техника,
   месяц без подписи договора, ПТК СТРОЙКОНСТРУКЦИЯ, «Берёзка» без
   подрядчика и т.д.).
10. Реестр критичных материалов и поставок (герметизаторы, изоляция,
    цемент, вилатерм, щебень, кабель, Ж/Б плиты, металлоконструкции) со
    статусами заявка→заказан→оплачен→в пути→на объекте/отсутствует.
11. Журнал решений и уведомлений, журнал изменений (аудит).
12. Дашборды: главная страница (прогресс/отставание/светофор/прогноз/
    дефицит/топ-5 причин/топ-5 ограничений), реестр работ с фильтрами,
    ресурсный дашборд, дашборд простоев, дашборд субподрядчиков, дашборд
    поставок, дашборд ограничений, ежедневная сводка (что делалось сегодня/
    что заблокировано/что планируется завтра), управленческий блок для
    Исполнителя (требовалось/выделено/дефицит/влияние на срок).
13. Batch-импорт Excel с преобразованием календарной матрицы в плоские
    таблицы, присвоением кодов, разделением план/факт, разбором текстовых
    комментариев в справочник причин, выделением подрядных отметок.
    **Валидация дат при импорте обязательна**: в исходном файле есть явные
    ошибки данных (даты герметизаторов «до 23.08.2027», «до 04.09.2032» и
    т.п. для объекта, который должен завершиться в 2026 году) — импорт
    должен флагать такие записи, а не проглатывать их молча.
14. HTTPS на `tm.asd-kontur.ru`, отдельная БД `tm35`, резервное копирование,
    изоляция от `bi.asd-kontur.ru`.

**Не входит в MVP (явно отложено):**
- Модуль симуляции («Дата→люди», «Люди→дата», сценарии, формулы дефицита) —
  2-я итерация. Схема данных (`scenario`, `scenario_result`) фиксируется в
  документации сейчас, чтобы миграция под неё не потребовала болезненного
  ALTER, но код и UI не разрабатываются.
- Специализации ресурса (монтажники/сварщики/...) — 2-й этап, как и в ТЗ.
- Telegram-бот — исключён полностью, не второй этап, а закрытый вопрос.
- Мобильный доступ без компьютера, экспорт в PDF/Excel — открытые вопросы
  ТЗ (п. 27), не обязательны для MVP, решаются по необходимости.

## Архитектура

```
Excel-файл (ПТО ИКС, ежедневно вручную)
        │  batch-импорт (изолированный процесс, устойчивый к
        │  merged cells / сдвигу колонок / новым месяцам)
        v
PostgreSQL "tm35" (отдельная БД на существующем VPS asd-kontur.ru)
        │
        v
Backend API (FastAPI/Node — на выбор реализации)
        │
        ├── Дашборды (веб, read-only для ролей Заказчик/Руководитель)
        ├── Журнал решений/изменений — доступен на чтение всем ролям
        ├── Управление реестрами (ограничения, субподрядчики, материалы) —
        │   доступно ролям Планёр/Администратор для ручного ведения
        └── Веб-форма ежедневного факта — опциональный второй канал ввода
            (роль Исполнитель), параллельный Excel-импорту, пишет в ту же
            модель данных (`daily_progress.source`)
        │
        v
Reverse Proxy (Nginx/Caddy) → HTTPS → tm.asd-kontur.ru
```

**Ресурсы на VPS** (8 GB RAM, общий с `bi.asd-kontur.ru`):
PostgreSQL 1–2 GB, Backend API 0.3–0.7 GB, BI/дашборд 2–3 GB (лёгкое
решение — Metabase/Superset или собственный фронтенд с серверной
визуализацией; приоритет — экономия RAM).

## Роли и права (скорректировано)

| Роль | Права |
|---|---|
| Администратор | полный доступ, настройки, пользователи, бэкапы |
| Планёр | ведение реестров (ограничения, субподрядчики, материалы, baseline с обоснованием), просмотр всех дашбордов |
| Исполнитель | опциональный ввод ежедневного факта через простую веб-форму — используется только если сотрудник ИКС сам выберет этот канал вместо Excel |
| Заказчик | только чтение дашбордов и отчётов |
| Руководитель | чтение дашбордов, аналитики |

Данные по ТМ-35 не должны смешиваться с данными на `bi.asd-kontur.ru`
(другой ОКС) — отдельная БД, отдельные права, как в ТЗ.
