## Итог одной строкой (на момент обнаружения)

Болезнь оказалась шире, чем считалось: `work.status` — статичное поле,
заполняемое при импорте и не обновляемое при вводе факта, — читается
для логики (не просто для отображения) минимум в **10 местах** кода,
из них исправлено (08.09, этой же сессией) только **3**
(`get_remaining_effort`, `works_with_baseline` в `get_criticality_data`,
`by_status` на `/dashboard`). Остальные **7** продолжают врать —
подробности ниже. У болезни нашёлся **близнец на другом поле**:
`change.overdue_days` (ИЗМ) обновляется только при правке записи, не
при течении времени. Отдельно найден **новый, не связанный** баг —
операторная ошибка Jinja в свежем фильтре `ru_money`, из-за которой
форматирование денег на трёх ИД-страницах сейчас снова сломано для
любой ненулевой суммы. Контур **РСК проверен целиком и находок не
дал** — единственный участок с последовательной архитектурой (общие
функции `compute_rsk_dashboard_stats()`, `rsk_pseudo_status()`, единый
`RSK_LIST_SELECT_SQL`).

## 3. ИД — врёт прямо сейчас *(✅ Находка №1 закрыта `0cfb324`, Находка №2 закрыта `27ea561`, дубль `amount_transferred` закрыт `46fa246`)*

**Находка №1 — новый баг, не про устаревшие данные.** В трёх шаблонах
(`id_folder_detail.html:33`, `id_folders.html:57`,
`id_folders_registry.html:67`) фильтр `ru_money` (введён сегодня же,
этой сессией) применён как `{{ X or 0|ru_money }}`. Приоритет операторов
Jinja2: `|` связывает крепче `or`, поэтому выражение читается как
`X or (0|ru_money)` — пока сумма ненулевая (обычный случай), на экран
идёт **сырое, неформатированное число** (точка вместо запятой, без
разделителя разрядов). Фикс форматирования тихо не сработал именно там,
где сумма реальна. Исправление: `{{ (X or 0)|ru_money }}`.

**Находка №2 — тот же диагноз, что у `work.status`, на другом поле.**
`change.overdue_days` вычисляется как `(today − planned_response_date)`
**только в момент** создания записи ИЗМ (main.py:4146), правки
(main.py:4270) или смены статуса (main.py:4048) — между этими
событиями столбец не течёт вместе с датой. Читается как готовое
значение в трёх местах без общей функции: `/changes` (main.py:4025),
форма с ошибкой в `changes_post` (main.py:4155), `change_stats_row` на
`/dashboard` (main.py:4426). Сегодня совпадает с живым пересчётом
(3=3) — совпадение случайное, не гарантированное: если запись не
трогать, «просрочено» не увеличится само с течением времени, ровно как
раньше не менялся `work.status`.

**Дубль — не текущая ложь, но риск.** `amount_transferred` на
`/id-folders/registry` (main.py:3790, Python `sum()` по списку)
дублирует `signed_folders_sum` из `compute_id_folder_stats()`
(main.py:3679, SQL `sum()`) — две независимые реализации одной суммы.

Проверено и чисто: `id_package` полностью выведена из кода (4
упоминания — все в комментариях); `ID_ROW_LIST_SQL`/`/id-packages` —
общая функция, живой расчёт; `compute_id_folder_stats()` — общая для
`/id-folders` и dashboard, фикс `money_remaining` применён
последовательно; `ID_FOLDER_CONTRACT_TOTAL` — легитимная константа
реального контракта, не подлежит вычислению из БД.
