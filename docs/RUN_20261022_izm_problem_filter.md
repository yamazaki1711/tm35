# Run log 22.10.2026 — ИЗМ: таблица и счётчики показывают только проблемные

Задание координатора 22.10.2026: таблица «Активные ИЗМ» на /changes
показывала все ИЗМ, включая «Техрешение получено» — «лишено смысла»;
показывать только те, по которым техрешение ещё не получено; данные
в БД не трогать. Уточнения координатора: плитка дашборда «Активных
ИЗМ (ДПР)» — то же правило («показывать 30 — демонстрировать застой»);
переключатель «показать все» одобрен.

## Правило

Проблемные = статус вне `CHANGE_RESOLVED_STATUSES` (SOLUTION_RECEIVED,
IKS_ORDER, INCLUDED_IN_RD, ARCHIVED) — существующая константа, не новый
список. На 22.10: 8 проблемных (IN_WORK_DESIGNER), 22 с техрешением.
БД не менялась вообще.

## Изменения (код — один атомарный коммит `2dc9869`)

1. `/changes` (`changes_page`): по умолчанию WHERE по правилу выше;
   `?show=all` — прежний полный список. Счётчики в заголовке — по
   показанному набору (дефолт: «всего: 8, просрочено: 8»; все: 30/8 —
   просрочка и так NULL у решённых, `_change_overdue_expr()`).
   Переключатель в заголовке: «показать все» ⇄ «только проблемные (N)».
   Смена статуса в строках работает в обоих режимах (ошибочно
   закрытый ИЗМ возвращается через «показать все», без БД).
2. Плитка «Активных ИЗМ (ДПР)» на /dashboard (`change_stats_row`):
   WHERE расширен с `not in ('INCLUDED_IN_RD','ARCHIVED')` до полного
   CHANGE_RESOLVED_STATUSES → 8/8 вместо 30/8.
3. Счётчик «Активных ИЗМ (ДПР)» на /id-folders (`active_changes`) —
   тот же WHERE (тот же счётчик, третья страница его показывающая;
   рассинхрон трёх мест показывал бы 8/8/30 — недопустимо).
