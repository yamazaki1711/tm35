# Фикс по жалобе В.М. Мельникова: «Снято» у №262 и невидимое сохранение отработки (20.10.2026)

Жалоба: «Раздел РСК — не могу сохранить вносимые изменения. Также фиксируется
среди снятых замеч. №262, в реальности — неснятое (мы раньше уже это
исправляли)». Диагностика и fix по двум пунктам, больше ничего не тронуто.

## Диагноз

**№262.** При импорте акта 4183-162 от 21.09.2026 нарушение №262 не было
найдено в акте → массовый структурный закрыв (`main.py`, confirm-импорт,
`update rsk_violation set is_active=false, closed_in_act_id=... where id =
any(...)`). Слой 2 при этом: `resolved=false` (актуально на 06.10.2026),
условие снятия «После получения протоколов уплотнения» — то есть ПТО считает
нарушение открытым («отложено до тёплого сезона»; впервые всплыло в
`docs/RSK_KONTUR_IMPORT_2026-09-06.md`, позиция 262). Критерий «снято» —
`not is_active or resolved` (`RSK_VIOLATION_REMOVED_SQL`) → №262 попадал в
«Снятые». Это тот же класс, что фиксы 24.09 («Снятые», 3 обращения) и 28.09
(№354, тихое закрытие матчером), но дыра другая: **отсутствие в акте вообще →
закрытие молча, без вопроса** — для отложенных нарушений срабатывает
гарантированно. Системная дыра (политика импорта) в рамках этой задачи НЕ
правилась — решение за координатором.

**«Не могу сохранить».** Сам POST `/api/rsk-processing` корректен (уточнено
по `rsk_processing.updated_ts`: правки №262 реально писались, последняя —
06.10.2026). Ломали UX три ветки:

1. Страница `/rsk/processing` не рендерила `&err=`/`&ok=` из редиректа
   POST-обработчика — и успех, и отказ выглядели как «ничего не произошло»
   (в `rsk_detail.html`/`rsk_import.html` баннеры есть, здесь — нет).
2. Форма рендерилась полностью редактируемой и для НЕвоnедшего пользователя,
   а POST без сессии отвечал 401 JSON (AuthMiddleware) — ввод терялся без
   объяснения.
3. Даже успешное сохранение было невидимо: №262 отсутствовал в рабочем
   списке (фильтр `v.is_active`) и карточка продолжала показывать
   «Статус: Снято» (правило двух слоёв — форма не трогает слой 1).

## Что сделано

1. **`backend/templates/rsk_processing.html`** (единственная кодовая правка,
   main.py НЕ менялся):
   - баннеры `flash flash-ok` / `flash flash-err` из query-параметров —
     тот же паттерн, что в `rsk_detail.html`;
   - редактируемая форма — только при `current_user`; для не вошедших —
     данные нарушения видны, вместо формы — сообщение и ссылка «Войти»
     (`next` с sys_no, urlencode).
2. **БД (прод), реактивация №262** — зеркально штатному POST
   `/api/rsk-violation/262/reopen`, без слияния:
   `update rsk_violation set is_active=true, closed_in_act_id=null where
   id=84` + запись в `audit_log` (action `rsk_manual_reopen`, user_id NULL,
   причина — жалоба Мельникова). SQL: на сервере
   `~/tm35_prod_snapshots/rollback_20261020_rsk_fix/fix_262.sql`.

Шаблон копирован в контейнер `docker cp` (горячая подгрузка, рестарт не
нужен). Проверено на живом стенде: №262 — «В работе», вернулся в реестр и в
список `/rsk/processing`, баннер ok рендерится, аноним видит блокировку,
смежные страницы 200.

## Открытым остаётся

Системная часть №1: нарушения, отсутствующие в новом акте, закрываются
автоматом и молча. Предлагаемое правило (на решение координатора): не
закрывать автоматически нарушения с незакрытым слоем 2 (`resolved=false`) —
отправлять их в ту же ручную очередь подтверждения, что конфликты матчинга
(28.09, №354).
