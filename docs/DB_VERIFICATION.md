# Проверка схемы на живом PostgreSQL — статус

**Итог: выполнено 15.08.2026, на сервере kat-core (`root@147.45.251.207`,
`asd-kontur.ru`), БД `tm35` внутри контейнера `kat_postgres`
(`pgvector/pgvector:pg16`, PostgreSQL 16.14).** Не локальный Postgres — от
той идеи отказались (см. историю задачи), локальная фоновая установка
`postgresql` на домашней машине завершилась сама, но не используется.

## Изоляция от Левашово/`bi.asd-kontur.ru`

- Существующая БД `kat_core` (владелец `kat_admin`, суперпользователь) —
  не тронута. `\l`/`\du` до и после создания `tm35` показывают, что
  `kat_core`, `postgres`, `template0/1` и роли `id_track`/`id_track_backup`
  не изменились.
- Отдельная БД **`tm35`**, отдельная роль **`tm35_app`** (`LOGIN`, без
  `SUPERUSER`/`CREATEDB`/`CREATEROLE`), `tm35` создана с `OWNER tm35_app`
  — по аналогии с тем, как `id_track` имеет права только на `kat_core`, а
  не на весь кластер. Пароль `tm35_app` сгенерирован отдельно (не
  переиспользован пароль `kat_admin`), хранится в
  `/home/oleg/Documents/TM-35/.secrets/tm35_app.env` (права 600, вне
  текста этого отчёта).
- Порт 5432 контейнера `kat_postgres` смотрит только на `127.0.0.1`
  сервера — снаружи недоступен. Для применения миграции и загрузки
  данных с этой (домашней) машины использовался временный SSH-туннель
  (`-L 15432:127.0.0.1:5432`), закрытый сразу после использования.

## Замечание по безопасности (зафиксировано, ничего не предпринято)

При разведке (шаг 1, до создания `tm35`) команда `docker exec kat_postgres
env` вывела переменные окружения контейнера `kat_postgres`, включая
**пароль суперпользователя `kat_admin` в открытом виде** — он прошёл через
вывод SSH-сессии этого чата. Сам пароль в этом отчёте не приводится.
Решение о ротации — не моя задача на этом шаге, действий не предпринимал.

## Применение миграций

```
migrations/001_init.sql → BEGIN ... 10×CREATE TYPE, 18×CREATE TABLE, 12×CREATE INDEX, 1×ALTER TABLE ... COMMIT
exit_code=0, без ошибок
```

В процессе первой загрузки обнаружился дефект, не пойманный на этапе
«вычитано вручную»: колонка «Объём работ» в исходном Excel тоже иногда
содержит текст вида `70шт` вместо числа (тот же класс дефекта, что уже был
известен для «% вып.», просто в другом поле) — `insert` в `numeric`-поле
упал с `InvalidTextRepresentation`. Не стал чинить схему вслепую поверх
уже применённой 001 — добавил отдельную `migrations/002_work_volume_raw.sql`
(`ALTER TABLE work ADD COLUMN volume_raw text`), применил её тем же
способом, обновил парсер и загрузчик. История миграций не переписана
задним числом.

```
migrations/002_work_volume_raw.sql → BEGIN, ALTER TABLE, COMMIT
exit_code=0
```

`\dt` на сервере после обеих миграций — 18 таблиц, все `Owner: tm35_app`.

## Загрузка данных — сверка чисел

Сверено независимым SQL-запросом к БД (не только по выводу
`load_to_postgres.py`):

| Что | Ожидалось (парсер) | В БД | Совпадает |
|---|---|---|---|
| `work` | 163 (main 105, aux 47, iks 4, rsk 7) | 163 (main 105, aux 47, iks 4, rsk 7) | да |
| `work.data_quality_flag='needs_review'` | 5 (см. DATA_QUALITY_REVIEW.md, группы A+B) | 5 | да |
| `daily_progress` | 4570 «сырых» записей план/факт → после свёртки по (работа, дата) в одну строку | 4428 строк | да, ожидаемо меньше сырых 4570 (не 1:1 — это правильно, см. ниже) |
| `daily_progress`, пропущено по неизвестному `work_id` | — | 0 | да |
| `import_unresolved_cell` | 5 (даты на границе месяца, группа C) | 5 | да |

Пояснение по 4570→4428: `daily_progress` хранит план и факт **в одной
строке** на (работу, дату), а парсер отдаёт план и факт **отдельными
записями**. 4570 записей — это не 2285 пар × 2 без остатка: часть дней
имеет только план или только факт без парной записи (например, будущие
плановые дни без ещё не наступившего факта), поэтому после свёртки
получается не ровно половина, а 4428 строк. Расхождение 4570 vs 2×4428
(=8856) объясняется этим и не является потерей данных — проверено, что
`skipped (work_id не найден) = 0`, то есть ни одна работа не осталась
несвязанной.

## Как повторить проверку

```bash
ssh root@147.45.251.207 -L 15432:127.0.0.1:5432 -N -f
TM35_APP_PW=$(grep -oP '(?<=tm35_app:)[^@]+' .secrets/tm35_app.env)
docker exec -i kat_postgres env PGPASSWORD="$TM35_APP_PW" psql -U tm35_app -d tm35 -c '\dt'
```
