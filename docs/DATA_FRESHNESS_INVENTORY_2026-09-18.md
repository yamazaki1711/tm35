# TM-35 — инвентаризация свежести данных по всем страницам (18.09.2026)

Задание координатора: подозрение, что `/quality` — архив, а не проверка,
подтвердилось (см. `docs/RUN_20260918_quality_page_and_data_freshness.md`
и уже переписанный `/quality`). Этот файл — тот же вопрос, заданный
КАЖДОЙ странице: что на экране посчитано только что, что прочитано из
метки, которую что-то пишет и никто не снимает, и что загружено один раз
из файла и больше не обновляется. Только чтение — ни одна строка БД не
менялась при составлении этого файла, все числа получены `select`.

## Итог, коротко

44 маршрута из собственной таблицы роутинга приложения (GET, без
параметров пути, без `/api/*`/`/static/*`/`/export/*`) плюс одна
страница с параметром (`/id-folders/{folder_id}`, добавлена вручную —
слишком важна, чтобы пропустить) — 45 строк ниже. Шесть из них не про
данные вообще (вход, две страницы настроек, два редиректа-заглушки,
служебный артефакт Swagger). Из оставшихся 39 подавляющее большинство —
живой расчёт по действующим таблицам. Настоящих находок три вида, все —
ниже:

1. **Одна не-«живая» цифра оказалась не тем, чем выглядит** — «Всего по
   контракту, ₽» на `/dashboard` и `/id-folders` читается из хардкода в
   Python, а не из таблицы `contract`, где те же данные (номер, стороны,
   дата, сумма) уже есть и не используются вовсе.
2. **Несколько экранов считают «трудоёмкость» по данным, которые
   перестали пополняться 29.08.2026** — не хранимая отметка в чистом
   виде (каждый раз честно пересчитывается), но исходный срез, из
   которого считается, заморожен уже почти три недели.
3. Обычный набор хранимых меток/разовых импортов — справочники,
   структурная конфигурация форм ИД, устаревшие столбцы.

## Живые расчёты на замороженном исходном срезе — самая широкая находка

Не хранимая отметка (SQL честно выполняется заново на каждый заход) и не
разовый импорт в чистом виде (страница НЕ читает готовое число из
таблицы-снимка) — третье, отдельное состояние, которого нет в
трёхчастной классификации задания буквально, но которое отвечает на тот
же вопрос координатора: **несколько ключевых цифр проекта считаются
живым SQL поверх данных, которые не растут с 29.08.2026.**

`get_remaining_effort()`, `get_evm_data()`, `get_today_data()` (все —
`backend/main.py`) считают «трудоёмкость» (план в человеко-днях по
каждой работе) как `sum(planned_crew) from daily_progress where
source='excel_import'`. Строк с этим `source` не прибавлялось ни разу
после 29.08.2026 (последняя `created_at` — `2026-08-29 00:17:31 UTC`,
проверено сегодня напрямую в БД) — сам Excel перестал быть источником
данных с 01.09.2026 (правило проекта, `CLAUDE.md`). Если у работы после
29.08 изменился объём/состав (новая работа, пересмотр объёма) — её
трудоёмкость в этом расчёте не появится и не изменится никогда, расчёт
просто не увидит новую работу в сумме (она провалится в
`excluded_count`, честно, не в 0, но и не в действительное число).

Затронутые страницы (все — через один из трёх перечисленных источников):
`/calculator` (прямо), `/status` (через `get_evm_data()`), `/dashboard`
(через `get_evm_data()` и `get_criticality_data()`→`get_remaining_effort()`),
`/today` (свой прямой запрос того же вида), `/critical` и `/` (через
`get_criticality_data()`), `/data` (тизер «Критичные работы», та же
функция). Это ровно та же схема, что и `baseline_schedule` выше
(легитимный на момент импорта разовый срез, используемый как живой
входной параметр) — не дефект по конструкции, а то, что стоит явно знать:
если объём работ по контракту меняется, этот расчёт узнает об этом,
только если кто-то заново прогонит `import/load_to_postgres.py` или
внесёт трудоёмкость новым путём, которого сейчас в приложении нет.
