# TM-35 — РСК «Снятые»: определение исправлено (структурно ИЛИ «Устранено»), 3-е обращение координатора (24.09.2026)

## Баг и его настоящая причина

`/rsk` → «Состояние» → «Снятые» → «Найдено: 0», хотя строки с заполненным
столбцом «Устранено» реально существуют. Прошлый заход (см. поправку в
`docs/RUN_20260924_tz10_followup.md`, §Пункт 3) проверил, что механизм
фильтра работает (доказано откаченной транзакцией), и что честный ноль
объясняется одним загруженным актом — но **не проверил, является ли
«структурное закрытие» единственным способом стать «снятым»**. Оно не
единственный: реестр отдельно хранит ВТОРОЙ, независимый признак —
«Устранено» (слой 2, форма отработки `/rsk/processing`), и он в фильтр
не входил вовсе. Определение было неполным, не сам SQL/UI-механизм.

## Шаг 1 — источник столбца «Устранено»

Таблица `rsk_processing` (форма отработки предписаний, слой 2 — миграция
038, 17.09.2026), два столбца:
- `resolved` — **boolean**, чекбокс «Устранено» на `/rsk/processing`;
- `resolved_date` — **date**, nullable, поле «Дата снятия» рядом с тем
  же чекбоксом.

Это НЕ свободный текст и не импортированное поле, не легаси-таблица
«Предписания РСК» — структурированная пара boolean+date, которую
заполняет сам ПТО через форму. Регистр `rsk_registry.html` показывает
её так: `{{ r.resolved_date|fmt_dmy if r.resolved and r.resolved_date
else ('да' if r.resolved else '—') }}` — дата, если она есть, иначе
«да», иначе «—». Каждое нарушение (`rsk_violation`) связано РОВНО с
одной строкой `rsk_processing` (проверено: 152 нарушения, 152 строки
`rsk_processing`, 0 нарушений без строки обработки) — многозначных
связей нет, документировать нечего.

## Шаг 2 — профиль реальных данных

```sql
select resolved, (resolved_date is not null) as has_date, count(*)
from rsk_processing group by resolved, has_date;
```

| `resolved` | Дата задана | Строк | Классификация |
|---|---|---|---|
| false | — | 136 | НЕ снято |
| true | нет | 14 | **СНЯТО** («да») |
| true | да | 2 | **СНЯТО** (дата) |

Итого «снято по б)» — **16**. Поле уже структурировано (boolean, не
текст) — **ни одного неклассифицируемого значения нет**, разбор
«да»/«Да»/«ДА»/дат в разных форматах, которого просил план задания,
физически не нужен: `resolved` не может содержать ничего, кроме
`true`/`false`, `resolved_date` — либо валидная дата, либо `null`.
Список REQUIRES COORDINATOR DECISION по этому шагу — пуст, не потому
что не искал, а потому что искать было нечего.

## Шаг 3 — одна функция, все потребители

`main.py`:
- `RSK_VIOLATION_REMOVED_SQL = "(not v.is_active or coalesce(p.resolved, false))"`
  — SQL-фрагмент для WHERE (использует alias `v`/`p`, уже присутствующие
  во всех запросах через `RSK_LIST_BASE_SQL`/`RSK_LIST_SELECT_SQL`).
- `rsk_violation_is_removed(row)` — тот же критерий над уже прочитанной
  строкой (Python dict/Row).

**Route through it — что изменено**:
- `rsk_registry_page()` (`/rsk`, «Состояние»): `state=active` →
  `not RSK_VIOLATION_REMOVED_SQL`, `state=closed` →
  `RSK_VIOLATION_REMOVED_SQL`. «Найдено: N» — тот же `len(rows)`, ничего
  отдельно считать не нужно.
- `rsk_pseudo_status(row)` — ветка «closed»/«Снято» (бейдж СТАТУС в
  реестре, `/rsk/processing`, карточке нарушения, CSV) теперь тоже
  `rsk_violation_is_removed(row)`, а не голый `not is_active`. **Это
  обязательная часть исправления, не факультативная**: без неё строка
  попадала бы в список «Снятые», но её собственный бейдж СТАТУС
  продолжал бы говорить «В работе»/«Готово к снятию» — новое
  расхождение «список против факта» того же класса, что уже чинили
  раньше (см. решение координатора: «so that Снятые и активные —
  точные дополнения»).
- `rsk_violation_detail()` (`/rsk/violation/{sys_no}`) — словарь,
  передаваемый в `rsk_pseudo_status()`, не содержал ключа `resolved`
  вовсе (только `is_active`/`rejected`/треки) — добавлен, иначе
  карточка одного нарушения показывала бы бейдж, расходящийся с тем,
  что видно в реестре для той же строки.
- `/export/rsk.csv` — читает `RSK_LIST_SELECT_SQL` и вызывает тот же
  `rsk_pseudo_status()` — унаследовал исправление автоматически, без
  отдельной правки логики «снято». Отдельно поймано и исправлено:
  колонка «Устранено» в CSV показывала пустую строку для 14 строк
  «да»-без-даты (`_csv_dmy(...) if r["resolved"] else ""` — не
  проверяла случай «resolved, но даты нет»), теперь то же правило, что
  и в таблице реестра: дата, если есть, иначе «да».

**Route through it — что НЕ изменено, и почему (сознательно, не
упущено)**:
- **Шесть плиток «Обзора РСК»** (`compute_rsk_dashboard_stats()`,
  `/rsk/dashboard` и блок «Обзор РСК» на `/dashboard`) — ВСЕ шесть
  остаются на чистом `v.is_active`. Они отвечают на другой вопрос:
  «из ещё СТРУКТУРНО не закрытых нарушений, в каком они процессе» —
  ровно то, ради чего заведён слой 2 (координатор, прошлое решение:
  «Устранено» — плитка специально показывает нарушения, отмеченные
  исполненными, но ещё числящиеся в последнем акте, не прячет их).
  Если бы «Активных замечаний» стало исключать `resolved=true`, а пять
  остальных плиток (Готовы к снятию/Предъявить ИД/Корректировка ПД-РД/
  Отклонено РСК/Устранено) остались на `is_active` — сумма процессных
  плиток могла бы превысить «Активных замечаний», новое, более заметное
  расхождение. Координаторская формулировка «Keep the two layers
  distinct in the data model. Only the filter/state definition unions
  them» прочитана буквально: «the filter/state definition» —
  единственное число, это и есть «Состояние»/бейдж СТАТУС реестра, не
  шесть отдельных метрик воркфлоу. Решение — в списке ниже, не решено
  самовольно молчанием.
- **`/rsk/processing`** (список для выбора нарушения на обработку) и
  **поиск кандидатов для привязки к разделу ИД** (`id_row_rsk_link`,
  функция поиска в форме ИД) — оба фильтруют только `v.is_active`, не
  тронуты: это рабочие списки «что ещё можно обрабатывать/привязать»,
  не отображение регистрового состояния — устранённое, но ещё активное
  нарушение по-прежнему может понадобиться доредактировать (поправить
  дату снятия, снять отметку по ошибке).
- **«Разрез по ответственным»** (`by_responsible`/`no_responsible` на
  `/rsk/dashboard`) — тот же аргумент, что и шесть плиток: нагрузка по
  ещё структурно открытым нарушениям, не по регистровому «снято».

## Шаг 4 — формат столбца «Устранено» не менялся

Таблица реестра — без изменений (дата/«да»/«—», как было). Только CSV
приведён к тому же правилу (см. шаг 3) — там раньше терялось «да».

## Шаг 5 — автоматическая проверка

`tools/check_consistency.py`, три новые проверки:
1. `/rsk?state=closed` («Найдено») vs прямой SQL по правилу (а)ИЛИ(б).
2. `/rsk?state=active` («Найдено») vs прямой SQL (НЕ снято).
3. «Снятые» + «Активные» = всего `rsk_violation` (полное дополнение,
   без пересечения и без пропуска).

## Живая проверка (24.09.2026, после деплоя)

| Показатель | Значение |
|---|---|
| Структурно снято (а) | 0 (один акт, как и раньше — не изменилось) |
| «Устранено»=«да», ещё активно (б, без даты) | 14 |
| «Устранено»=дата, ещё активно (б, с датой) | 2 |
| **Пересечение (а) и (б)** | 0 (ничего структурно закрытого сейчас нет вовсе) |
| **«Снятые» (Найдено) на `/rsk?state=closed`** | **16** |
| «Активные» (Найдено) на `/rsk?state=active` | 136 |
| Всего `rsk_violation` | 152 |
| 16 + 136 | 152 ✓ |

Точечная проверка (не выборочно на глаз, реальные `sys_no`): 3 строки
с «да» (100, 151, 327) и 2 строки с датой (163, 164 — все существующие
строки с датой, их всего 2) — все пять: `grep` подтвердил присутствие
ровно один раз в HTML `/rsk?state=closed`, ноль раз в `/rsk?state=active`;
`rsk_pseudo_status()` для всех пяти вернул `closed`/«Снято» — бейдж
согласован со списком. CSV-экспорт для sys_no 100 → Статус «Снято»,
Устранено «да»; для sys_no 163 → Статус «Снято», Устранено «17.08.2026».

Другие значения «Состояние» — «Активные» (136) и «Все» (152, дефолт без
параметра) — работают, суммы сходятся (16+136=152=total).
