## 04:4x — Важный пробел в данных, обнаруженный ДО написания дашбордов

Часть обязательных полей ТЗ п.10 физически не заполнена в БД после
парсинга Excel (это не решение, а константация факта, важная для
трактовки того, что покажет дашборд):

- `baseline_schedule` / `current_schedule` — **пусты**. Excel не содержит
  явных дат начала/окончания по работе (только «Месяц выполнения работ»
  текстом и календарную матрицу План/Факт по числу людей) — парсер их и
  не извлекал. Следствие: «отставание в днях», «прогноз завершения»,
  светофор по срокам из ТЗ 10.1 **не могут быть посчитаны** без этих
  таблиц.
- `resource_pool` — **пуста**. В Excel есть строка «Итого кол-во человек»
  по каждой секции листа, парсер её сейчас явно пропускает
  (`is_totals_row → continue`), не сохраняя. Ресурсный дашборд буду
  считать прямой агрегацией `daily_progress` (SUM planned/actual по
  датам), а не из `resource_pool`.
- `daily_progress.reason_code` — **не размечен** (парсер сохраняет только
  исходный текст комментария, не мапит на закрытый справочник причин
  ТЗ 8.8). Дашборд простоев покажет группировку по фактическому наличию/
  отсутствию комментария и сами тексты, не по кодам причин.
- `blocker` / `subcontractor` / `material` — **не заполнены** (парсер
  извлёк метку «Подряд»/название субподрядчика в `work.subcontractor_note`
  как текст, но не создал структурированные записи в этих таблицах —
  отдельный шаг миграции данных, не входил в объём предыдущей задачи).

**Решение на эту ночь:** не подделывать эти разделы фиктивными цифрами.
Каждый раздел дашборда, зависящий от пустой таблицы, показывает явное
«данные не загружены» + причину, а не нулевые/придуманные значения.
Дозаполнение этих таблиц из Excel (парсер секций «Итого», парсер
subcontractor-меток в структурированные записи, маппинг причин простоя) —
**в список «требует решения координатора»**: не мелкая доработка, а
отдельный кусок работы над парсером, не блокирует публикацию MVP-каркаса
дашборда.

## 06:0x — Проверка глазами (Playwright) по запросу координатора, нашлась и исправлена реальная недоделка

Координатор попросил открыть сайт браузером и посмотреть самому, заметив,
что «выглядит как заготовка». Playwright не был установлен — поставил
(`pip install playwright` + `playwright install chromium`, ~185 МБ,
локально на этой машине, не на сервере). Скриншоты — `deploy/screens*.png`.

**Реальная находка, не ложная тревога:** `work.status` был `not_started`
у всех 163 работ без исключения — парсер никогда не выводил статус из
`% вып.`, поле просто оставалось на дефолте схемы. Отдельно —
`work.location` (участок) был `NULL` у всех работ: в самом Excel нет
отдельной колонки «Участок», код участка (УТ13, УУСА1 и т.п.) зашит
подстрокой в наименование работы, парсер его не извлекал. Отдельно — 20
из 23 дневных комментариев-стопфакторов не долетали до `blocker`, потому
что парсер проверял комментарии только в колонке «План» дня, а часть
стояла на колонке «Факт».

**Исправлено в `import/parse_excel.py`:**
- `derive_status(fact_pct)`: 100% → `done_physically`, 0<x<100% →
  `in_progress`, нет данных → `not_started`. Осознанно НЕ ставлю
  `closed`/`accepted` — ТЗ 11.4.5 прямо предупреждает, что 100% физически
  ≠ принято/закрыто, а этого мы не знаем из Excel.
- `guess_location(name)`: regex по известному из ТЗ 8.1 набору кодов
  участков, ищет первое совпадение в наименовании. Сработало на 146 из
  163 работ (17 — без определимого участка в тексте, это ожидаемо для
  части «вспомогательных» работ типа «Погрузка материалов на Фокино»).
- День-уровневые комментарии теперь проверяются на ОБЕИХ колонках дня
  (План и Факт), не только на «План»: было 3 найденных комментария, стало
  23.

**Исправлено в `import/load_to_postgres.py`** (заодно, при повторном
прогоне): `import_unresolved_cell` и `blocker` (день-уровневые) не имели
защиты от дублирования при повторном запуске — первый же повторный
прогон задвоил `import_unresolved_cell` (5→10). Добавлено `delete` перед
`insert` в обеих функциях, идемпотентность перепроверена двумя прогонами
подряд — числа не растут.

**Побочная находка, тоже исправлена:** свой же `scp` с опечаткой в пути
(`tm-app/../`) уронил `parse_excel.py`/`load_to_postgres.py` прямо в
`/opt/kat/` на сервере — не нужны там (импорт запускается только с этой
машины через SSH-туннель в БД, не из контейнера). Удалил сразу же, как
заметил.

**Итог после исправления** (проверено скриншотами, не только SQL):
статусы — 99 not_started / 50 done_physically / 14 in_progress; участок
