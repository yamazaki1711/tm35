# Структура исходного Excel-файла ТМ-35

**Область применения (уточнено 18.08.2026).** Этот skill описывает
только канал контура **СМР** (график работ ПТО ИКС). Данные контура
**ИД** (смета, пакеты ИД, вопросы к РД, предписания — из Google Drive
по докладу координатора) сюда не входят и структурно не разобраны —
см. `CLAUDE.md`, раздел «Требует подтверждения».

Разобрано на файле `График работ до завершения стройка_ИКС_РСК 13.08 (2).xlsx`
(снимок на 13.08.2026, лежит в корне проекта). Актуальность структуры
метаколонок нужно перепроверять при каждой новой присланной версии файла —
человек ведёт его вручную, порядок и состав колонок между версиями может
плыть.

**Обновление 20.08.2026 — с этого снимка канонический файл содержит
только 1 лист, не 3.** Новый снимок `График работ до завершения
стройка_ИКС_РСК 16.08.xlsx` (тоже лежит в корне проекта, старый снимок
13.08 оставлен рядом для истории) содержит только основной лист
(«График завершения работ по ТМ35»); листы «График по замечаниям ИКС»
и «График по замечаниям РСК» намеренно удалены **по прямому
распоряжению главного инженера** (передано координатором) — это не
дефект файла и не повод переоткрывать структуру, `import/parse_excel.py`
штатно обрабатывает отсутствующие листы как `sheet_missing` и продолжает
с тем, что есть. Структура оставшегося основного листа (метаколонки,
календарная матрица) не изменилась между 13.08 и 16.08 — тот же
парсер сработал без правок кода. При следующей версии всё равно
свериться (могли не только листы поменяться), но отсутствие ИКС/РСК
самих по себе больше не аномалия. Полный разбор различий между 152
работами (main+aux) старого снимка и 146 нового — `CLAUDE.md`, раздел
«Обновление канонического файла ПТО на 16.08.2026».

## Общий принцип (одинаков для всех 3 листов)

Каждый лист = «шапка метаданных работы» (колонки A..) + «календарная
матрица» (день за днём, План/Факт), считанная построчно, одна строка = одна
работа, плюс служебные строки-разделители секций и итоговая строка по
людям.

Структура по строкам:
- **Строка 1** — заголовок листа (в одной ячейке A, с большим отступом
  пробелами).
- **Строка 2** — шапка колонок метаданных (merged по вертикали до строки 4)
  + merged по горизонтали заголовки месяцев над календарной частью
  (`ИЮНЬ`, `ИЮЛЬ`, `АВГУСТ`, `СЕНТЯБРЬ`, `ОКТЯБРЬ`, `НОЯБРЬ` — на снимке от
  13.08 доходит до ноября; при новом месяце лист расширяется вправо).
- **Строка 3** — номер дня месяца (1..31) в первой колонке каждой пары
  день-колонок. У колонок-«выходных» (см. ниже) в строке 3 значения нет.
- **Строка 4** — подписи `План` / `Факт` под каждой парой колонок дня.
- **Строка 5 и далее** — данные: либо строка-работа, либо служебная
  строка-разделитель секции, либо итоговая строка в конце листа.

## Метаколонки (A..I) — состав РАЗНЫЙ на каждом листе

Не считать состав одинаковым по буквам колонок между листами — сверять по
заголовкам строки 2, не по букве.

| Лист | Колонки метаданных | Календарь начинается с |
|---|---|---|
| «График завершения работ по ТМ35» | A № п/п, B Наименование работ, C Ед.изм., D Объём работ, E Кол-во чел., F «Месяц выполнения работ» (заголовок-заглушка над всей календарной частью, самих значений в ней нет), G % вып., H Вид техники, I Примечания | J |
| «График по замечаниям ИКС» | A № п/п, B Наименование работ, C Ед.изм., D Объём работ, E Кол-во чел., F % вып., G Вид техники (нет колонки «Примечания» и нет F-заглушки) | H |
| «График по замечаниям РСК» | A № п/п, B Содержание работы, C Порядковый номер в реестре, D Наименование работ, E Ед.изм., F Объём работ, G Кол-во чел., H % вып., I Вид техники | J |

На листе РСК `№ п/п` (колонка A) хранится **строкой**, не числом — приводить
типы явно, не полагаться на `isinstance(v, int)`.

## Календарная матрица: день = 2 колонки, ВЫХОДНОЙ = 1 колонка без заголовка

Обычный рабочий день — пара колонок (План, Факт), с номером дня в строке 3
над первой из пары. Между некоторыми днями встречается **одна лишняя
колонка без номера дня и без подписи План/Факт** — это выходной день;
в строке данных для него может стоять литерал `В` (в самой ячейке значения,
не в шапке).

Определять день недели по этой колонке нельзя надёжно (она просто вставлена
как визуальный разрыв) — день недели считать по фактической календарной
дате (месяц из строки 2, число из строки 3 соседних колонок), а не по
наличию/отсутствию колонки-разрыва. Наличие/отсутствие самой колонки — это
подсказка «здесь выходной», не источник даты.

Алгоритм разбора одной строки календаря:
1. Пройти по строке 3 слева направо, для каждой непустой ячейки — это
   начало пары (План/Факт) для дня N текущего месяца (текущий месяц берётся
   из последнего пройденного merged-заголовка строки 2).
2. Следующая колонка — Факт того же дня (проверять строку 4: `Факт`).
3. Любая колонка между двумя такими парами, где строка 3 и строка 4 пустые
   — колонка-разрыв (обычно выходной); её значение в строке данных (часто
   `В`) — не план/факт, а флаг нерабочего дня, использовать для
   `daily_progress.status = 'выходной'` или пропускать без создания записи
   плана/факта, но не терять сам факт «был выходной».

## Секционные строки и итоговая строка

Внутри одного листа несколько блоков работ, каждый со своим заголовком:
- Строка, где колонка A содержит **текст**, а не номер, и остальные
  метаколонки пусты — это заголовок секции (например, `Работы по
  устранению выявленных недостатков при строительстве`, `Работы
  неучтенные в основном графике`). Использовать как значение поля
  `work.source`/группировки, не как отдельную работу.
- Последняя такая строка в каждом блоке — `Итого кол-во человек` — это
  **не работа**, а сводка по дням: в календарных колонках вместо
  План/Факт лежит суммарное число человек за день (например,
  `21 чел.`) или просто число. Использовать как источник для
  `resource_pool` (проверка целостности: сумма `daily_progress.actual_crew`
  по всем активным работам за день должна соотноситься с этой цифрой, а не
  обязательно совпадать один в один — вспомогательные работы считаются
  отдельно).
- После итоговой строки в файле могут быть сотни пустых форматированных
  строк (артефакт заполнения листа стилями) — останавливать парсинг по
  первой строке, где колонка A пуста три раза подряд после начала данных,
  а не по `ws.max_row`.

## Комментарии (Excel notes) — источник стоп-факторов и WORK:-пометок

Причины простоя и пояснения лежат не только в значениях ячеек, но и в
**комментариях к ячейкам** (`cell.comment.text` в openpyxl, а не
`cell.value`). Парсер обязан сканировать `.comment`, а не только `.value`,
иначе теряется существенная часть данных. Встречаются два разных паттерна:

1. **Комментарий на ячейке дня в строке работы**, часто с префиксом
   `WORK:` — относится конкретно к этой работе в этот день
   (`DQ11: "WORK:\nУстранение замечаний "`). Это и есть «комментарии
   WORK: ...» из ТЗ п. 11.2 — парсить как причину простоя/примечание к
   конкретной записи `daily_progress`.
2. **Комментарий на ячейке заголовка дня (строка 3)** — встречается как
   общая пометка на весь день, иногда с указанием ФИО ответственного
   (`DD3: "Сметаненко Тимофей Евгеньевич:\nОтсутствие техники из за
   топлива"`). Трактовать как день-уровневый стоп-фактор (кандидат в
   `blocker`/`resource_pool.comment` за эту дату), а не как факт по
   конкретной работе — привязки к строке работы там нет.

Не считать отсутствие `WORK:`-префикса признаком «не стоп-фактор» — текст
без префикса тоже нужно сохранять как есть (ТЗ требует хранить исходный
текст, п. 11.4.3), а не отбрасывать то, что не подошло под шаблон.

## Отметки о субподряде

В колонке «Кол-во чел.» встречается не число, а литерал `Подряд` / `ПОДРЯД`
— означает, что работа выполняется субподрядчиком, а не числом человек
исполнителя. При этом:
- в колонке «Примечания» (там, где она есть) — название субподрядчика и
  номер/дата договора одним текстовым блоком, например: `Подрядчик ПТК
  СТРОЙКОНСТРУКЦИЯ №19447/СУБ/240814\nДата окончания работ 16.11.2026` —
  парсить регулярным выражением на `Подрядчик <название> №<номер>` и
  `Дата окончания работ <дата>`, но не терять исходный текст при неудаче
  разбора;
- в самих ячейках календаря того же ряда literal `ПОДРЯД` может стоять
  вместо План/Факт числа — значит в этот день работу вёл субподрядчик,
  собственных человеко-часов ИКС не было.

## Известные дефекты данных (подтверждены на снимке 13.08, см. также ТЗ п. 11.4)

- `% вып.` — вперемешку числа-проценты (100, 5, 90...), значения с
  суффиксом `шт` (это физический объём, не процент: `16шт`, `9 шт`) и
  пустые ячейки. Нормализовать по правилу ТЗ 11.4.2: суффикс `шт` →
  физический объём + отдельное поле «исходное значение», пусто → «не
  указан».
- Даты поставок (герметизаторы и т.п., где встречаются в примечаниях) —
  попадаются годы 2027–2032 для объекта, который должен завершиться в
  2026 — флагать как сомнительные (ТЗ 11.4.1), не отбрасывать и не
  принимать молча.
- Множественные причины простоя в одном комментарии через запятую
  (`Осадки в виде дождя,отсутствие ГСМ`) — разбивать на отдельные записи
  реестра ограничений, сохраняя исходный текст целиком отдельным полем.

## Что перепроверить при новой версии файла перед правкой парсера

- Не сдвинулся ли состав метаколонок A..I на каждом листе (сверять по
  тексту заголовков строки 2, не по буквам).
- Не появился ли новый месяц справа (парсер должен идти по merged-
  заголовкам строки 2, а не по жёстко заданному диапазону колонок).
- Совпадает ли число листов и их порядок (основной / ИКС / РСК).
